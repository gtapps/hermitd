# Access model

Access is owned by the existing channel, native settings, and hermit configuration surfaces. There is no separate hermit access registry.

## Approvers

The channel plugin relays native permission prompts to the DM-paired `allowFrom` list. Pair only people who may approve tool use. An empty list reaches nobody. In `approvals: "personal"` an unattended prompt waits. In auto mode, `approvals: "team"` refuses it. Use `/hermitd:channel-access` to unpair an approver. Removing their DM relay leaves their group membership and earlier approvals in place. The agent warns when the last approver is removed or the person retains primary operator authority. Pair a new approver from the terminal. See **Settings from chat** in [security](security.md#auto-mode-classifier).

Only the agent's primary operator may request a standing classifier approval-rule change through `/hermitd:hermit-settings rules`; other participants are told an admin must set it. A terminal operator may also request one. The native prompt still decides each edit, and a classifier `allow` cannot override native ask or deny rules.

With `approvals: "team"` (effective at the next start), a prompt appears only on the main loop after the latest prompt was typed at the terminal or in the Claude app, or came from a DM-paired approver in the maintainer chat itself, without a thread. The chat prompt closes after 60 seconds; typed prompts have no deadline. A late approver message there can let earlier work prompt for up to 60 seconds, and only Allow runs it. A late member message disables prompting. Every prompt that appears still sends Allow / Deny to the DM-paired users. Subagents, helpers and background sessions opened from the app never prompt. `personal` is the default and preserves existing behavior without an extra approval process.

The maintainer chat is the admin console for refused chat requests. Point `maintainer_channel_id` at an admin's DM or private admins group that the agent listens in; enroll groups and address the agent under the channel's mention rule. Everyone there can read requests. Anyone admitted there may answer a request, but only a DM-paired approver's reply there leads to a native prompt. A non-approver's yes is refused and the question reopens. If the console cannot be reached the request is not delivered and the asking chat is told. An admin can also use the terminal or Claude app. Chat approval needs a pairing list and permission relay; channels without them cannot approve from chat. Unattended refusals send one notice and open no task.

A refusal before a prompt sends no approval DM. A prompt that still opens on a refused turn closes at once, although its DM may already have gone out. Immediate and timed declines are dismissals toward deny only, including question and plan-approval dialogs. A failed approval check refuses and is reported; an entirely unreachable bridge leaves the mode unknown and behaves as personal. To stop a step asking for everyone, an approver can ask in the maintainer chat to delete its `permissions.ask` entry. Deleted offered entries stay deleted across setup and upgrades, except that upgrading from before 1.4.24 re-adds them once before stamping the record.

## Participants

Groups own admission independently of the DM `allowFrom` list. Hermit `channels.<name>.allowed_users` narrows who can wake the hermit. Absent means accept all delivered senders, while `[]` accepts none. New team channel setups leave it unset and recommend allowing anyone in each enrolled chat. Personal setup recommends the paired sender alone. Whenever setup leaves the list open, it sets `operators` to the paired ID if the key is absent. Existing access lists survive upgrades.

For plugins using the official access file, use `/hermitd:channel-access` to show access, add or remove named senders, open a chat to everyone, or stop listening in a chat. Adding someone may also require appending their ID to an existing `allowed_users` list. Its first entry is primary when `operators` is absent. For a team, make the request as a paired approver in the admin chat and approve the native prompt in a paired DM. A member's request asks the admin chat first. In personal mode the plugin relays the prompt to the paired DMs. See [channel configuration](config-reference.md#channels) and [known limitations](security.md#known-limitations).

A member's requested watch is saved disabled until a primary sender says yes in that chat. A no leaves it disabled.

**Members-only channels.** `channels.<name>.members_only: true` turns off every elevated path on that channel: trusted-controller commands, primary-operator and sign-in authority, unscoped recall from a home or maintainer chat, home pinning, and notice routing. Every sender is a member, the operator included; the operator keeps their authority on their other channels. `allowed_users` still decides who is admitted.

**Connector chats.** Each person paired through the [connector](connector.md) gets their own chat, isolated by default. Listing it in `shared_chats` shares it with every chat on every channel, so do that only where every chat on the agent is the operator's own.

**Recall scope.** Per-channel `isolate_chats` and `shared_chats` own channel-log visibility: own chat by default, the whole channel when isolation is false, plus listed shared chats from any configured channel. Removing a shared id removes that grant; removing `isolate_chats` restores isolation. The maintainer chat is always unscoped, and the home chat is unscoped only on a technical profile. A home chat pinned to a shared group therefore gives every member of it unscoped recall across every chat on every channel, the same standing exposure the control-command rule has — set `allowed_users` and keep the pin on a real DM to narrow it. An unknown channel sees only itself. Terminal search is unscoped. Briefs follow the recall scope of the chat they answer in and also count records in that chat's public threads. Shared-chat grants do not expand to their children; private threads are not rolled up. Briefs require `--agent`, `--chat` or `--routine`; terminal and Remote Control use `--agent`. Chat briefs list decisions on visible conversation records. Briefs to any chat other than the home chat omit null-conversation admin decisions, duties and priorities and skip upgrade checks and dashboard refresh; the home chat keeps them on every profile. Compiled pages are scoped by frontmatter `audience` (`shared` or `<key>:<chat_id>`; absent means `shared`). Session reports and proposals are operator material, unavailable to scoped readers. The resident's own context is shared across chats for non-task turns.

**Operators.** `channels.<name>.operators` names the admin for agent-wide standing roles, approval rules, watch approvals, and tool sign-in. Removing it restores the first-allowed-user rule; without `allowed_users`, the maintainer chat or technical-profile home chat qualifies. When a group is the maintainer chat or the home chat on a technical profile, and the channel has neither `operators` nor `allowed_users`, every member of it, including in its public threads, counts as admin for decisions and proposal consent; set `operators` to name the admin. Without any of these fields nobody is primary. When `operators` or `allowed_users` names people, the agent's pending questions in a chat take answers only from the admin, or from the member a question was asked of about their own request; otherwise authority follows the primary-operator rule. Chat input decisions admit allowed members of that chat, and requester decisions admit the named requester or an admin. A chat decision, close, cancel or clear-wait that names a sender is refused unless that sender's message opened or joined the current turn, so terminal and wake turns cannot name one. Proposal consent always requires an admin. Terminal answers use `task answer <id> --local --reply yes` ([when it prompts](task-records.md#proposals-and-durable-questions)). Other admitted senders save roles pinned to their current chat and cannot change hermit-wide rules. This list also owns control commands (below). It does not own native prompt delivery and never bypasses admission. Existing roles remain as saved.

**Chat instructions.** `channels.<name>.instructions` holds operator-set policy for individual chats, ahead of memory roles. Every add, change or removal needs native approval, subject to the `approvals` turn gate above. Approvers are the DM-paired `allowFrom` users, not `operators`; admitted members can still save memory roles without changing these instructions.

## Control commands

Bare `!release` uses the same trusted-controller gate as pause. It releases human browser control, keeps the task claim, and reports whether anything was held. Other senders cause no state change or response.

Control commands (`!pause`, `!stop`, `!resume`, `!snooze`, `!release`, `!model`, `!effort`, `!compact`, `!clear`, `!advisor`, `!doctor`) and full `!status` belong to the operators: the `operators` list, or the first `allowed_users` entry when `operators` is absent, or the maintainer chat or technical-profile home chat when neither list is set. With neither list, the pinned `default_chat_id` also controls on any profile; without a matching home chat there is no controller. A shared home matches every member, so set `operators` to narrow control there. Other admitted senders get a short refusal and a coarse `!status`; senders who are not admitted get no response. Removing the lists restores the home-chat fallback. The saved list and home pin survive restart; a new inbound DM does not move the pin. This rule does not own native approval delivery. Separately, adding a listening chat through `hermit-settings channels` asks for native approval and is refused under bypass permissions. See [security limitations](security.md#known-limitations).

## Connections

Each tool uses one account for every chat and routine in the resident. Anyone admitted may ask to reconnect it, but only an admin may finish sign-in, with `/mcp` at the agent's terminal: a callback pasted in chat cannot finish it. Authority follows the control-command rule below: the operators, and the pinned home chat when neither `operators` nor `allowed_users` names people. Explicit empty lists grant nobody authority. Someone typing at the terminal can also finish it; a turn nobody typed, such as a routine, a peer wake or a background helper, raises the native permission prompt, and so does any turn such a wake or another sender joins midway. Prefer a dedicated account and forward the link `/mcp` shows if someone else owns the tool account. The same rule covers API keys and git credentials: a dedicated service account, API key, or GitHub App for this agent. Revoking that credential cuts the agent off. Different access requires separately configured residents.

Native settings own project MCP enrollment through `enabledMcpjsonServers`, `enableAllProjectMcpServers`, and `disabledMcpjsonServers`. Without approval, a project server stays pending without blocking boot. Remove approvals in every applicable native scope, including blanket approval, or explicitly disable the server to exclude it at restart. Removing enrollment does not delete its declaration or credentials. A temporary `/mcp` toggle does not remove the saved approval.

Account connectors are added and authorized on claude.ai, and each one reaches every chat the agent serves, so a shared agent belongs on a dedicated account. See [Claude Code MCP](https://code.claude.com/docs/en/mcp). Native `disableClaudeAiConnectors` owns account connector loading. When unset, a login-authenticated hermit loads account connectors; setting it to `true` disables them for the project without deleting account connections. Removing the setting restores default loading at restart. Setup-token authentication fetches no account connectors. See [MCP servers](always-on.md#mcp-servers).

## Browser phone takeover

Managed browsers on Docker and hosts work without takeover setup for public pages. Phone sign-in is opt-in: `/hermitd:browser` collects a short `browser.admins` list in chat through the native-prompt settings route, asks for one host `hermitd run browser-host` command, verifies it, and declares one `browser-handback` stream monitor. Existing hermits receive the browser through upgrade; viewer access remains opt-in.

Takeover needs Tailscale. Docker also needs server 28.0.0 or newer and an image whose `/etc/hermit/managed-browser` marker contains `display=plugin`. The plugin owns display startup independently of the entrypoint; older bare markers require `hermitd update`. For an unconverted install, run `/hermitd:docker-customize "Convert"` before the host rebuild. It publishes one loopback port and uses tailnet-only Serve, never Funnel. Linux/WSL2 tmux hosts use the same command for prerequisites and display startup; macOS hosts outside Docker and interactive hermits refuse takeover; Docker Desktop host-networking loopback reachability remains unverified and a failed route check is reported. No image rebuild is needed for takeover on an image already carrying the managed browser.

Only an exact allowlisted Tailscale user login may load the viewer or its WebSocket. A tagged phone has no user identity and is refused. After checking identity, the viewer checks Host against `browser.host:browser.port`. The page checks Origin against Host for Take over, Hand back and the socket upgrade. There is no watch mode: the newest Take over wins and closes older sockets. A dropped connection keeps control until Hand back, trusted-controller `!release`, browser loss, or 30 minutes without a viewer. Anonymous headless tasks can continue during human control; signed-in tasks share one claimed profile and queue.

The login request stays in its original conversation and mentions the admin using the configured handle for that channel. Its `?task=<id>` link names the waiting task. Hand back leaves Chrome and its page running. A durable event wakes the resident; the task writer conditionally clears only the matching `waiting_since`, then the agent checks the expected page and account before continuing once. Forced release, expiry and browser loss wake it too, without claiming sign-in succeeded. The viewer never writes task records. When a secret store is prepared, the preparing task can only run `store-copied` or close the signed-in browser. The store reads the clipboard only after a hand back for that task. A new claim holder triggers cleanup before its first persistent browser command.

This checks tailnet identity, not the agent's honesty: the agent inside the container, a host process reaching loopback, or another container reaching port 6080 on the same Docker network can forge the identity header. See [known limitations](security.md#known-limitations).

With team approvals, only an admin at the host terminal saves or deletes a login using `hermitd run browser-agent save-login` or `hermitd run browser-agent delete-login`.

## Unattended settings writes

`channel-access.ts` manages the official `access.json` format for any configured channel. Enrolling a chat writes `config.json` before the access file. Turning off a chat removes access first and then clears its passive and shared settings. If the second write fails, the command reports `partial_config_written` or `partial_access_written` and tells the operator to rerun it. Plugins can write `access.json` concurrently, which can overwrite one writer's changes. Official Discord and Telegram reload access for incoming messages unless configured for static access, which needs a restart.

The settings gate asks on recognized direct writes into the configured channel state directory outside `inbox/` unless the turn was typed at the terminal or in the Claude app. Bypass mode refuses such writes on chat and unknown turns. Shell expansions and the Claude home fallback file are outside this check. See [known limitations](security.md#known-limitations).

The shipped `SEALED_SETTINGS_OPS` list owns the enumerated classifier exception, rendered into a per-session overlay at each boot. An absent op has no exception from this list. Removing an overlay entry by hand does not persist across restart: boot renders it again from the installed list. The exact constraints remain in [the sealed exception](security.md#auto-mode-classifier).

Boot separately owns local settings keys and terminal-only operations, including voice rendering and artifact revocation. These run outside a session; a chat decision records config rather than executing the revoke. Unset behavior depends on the key: language clears its local mirror, voice leaves the operator's pick alone, and artifact authorization leaves an existing grant alone. Removing a generated local value is not a durable opt-out when configured boot ownership still applies.

## Preferences

Hermit `model` and `effort` are launch flags only when set. Unset values pass no override and leave native defaults in charge. Removing either override stops reasserting it at restart without deleting native settings; a configured override returns at restart after a runtime change.

Hermit `language` is carried by the resident launch overlay when configured. Clearing it leaves native preferences in charge. The native `/config` Language picker writes user scope and survives restart.

Hermit `voice.style` owns the launch overlay `outputStyle` when configured. `voice.style: null` leaves the operator's pick alone, including an existing rendered value; clearing the config is not deletion of the style or custom style file. A configured style is reasserted at restart. See [configuration](config-reference.md).

## Upgrades

Installed plugin code owns shipped permission registries; hermit config and native settings retain their existing owners through upgrades. There is no new access key or enrollment conversion. An unset preference or enrollment remains subject to its surface's defaults, not a second access registry. Permission sync removes only named obsolete rules and preserves other operator entries. Removing a canonical grant by hand can be undone by permission sync; removing a boot-owned value can be undone at restart while its config still applies. Operator-authored state survives except for explicitly documented migrations. See [security](security.md#auto-mode-classifier) for the upgrade-triggered sealed exception.

## Revocation

An explicit `artifacts.publish_authorized: false` removes exactly `Artifact` from `permissions.allow` at the next boot, preserving all other entries and keys. It clears every settings file the plugin wrote the grant to: the local one, which the boot grant re-ensures, and the committed one when `state/hatch-options.json` stamps the hatch target `committed`. An install carrying no usable stamp is cleared locally only, because an unstamped entry's provenance is unknown. An absent entry is a no-op, and costs no subprocess. A `null` decision leaves an existing entry alone. Disabling pages or switching backend alone does not revoke an existing grant; `true` re-ensures it only when a page is enabled and the backend is the default Claude backend.

Removal takes effect through the next boot, not immediately in the current session. It removes this standing permission, not previously published pages, banked URLs, account sharing, or permissions in other scopes. The declined decision survives restart and continues to enforce removal. See [artifact authorization](config-reference.md#artifacts) and [security limitations](security.md#known-limitations).

Avoid shared hosts: a local user can reach Chrome’s debugging port or forge the loopback login header. Xvnc runs without `-auth`. The Linux phone test is the manual pre-merge gate; macOS hosts and WSL2 remain unverified by a live run.
