# Access model

Access is owned by the existing channel, native settings, and hermit configuration surfaces. There is no separate hermit access registry.

## Approvers

The channel plugin's DM-paired `allowFrom` list owns native permission-prompt delivery and approval. DM-pair only people who may approve tool use: every listed DM receives and can answer prompts. An empty list reaches nobody, so an unattended prompt waits. Removing a person from this list removes their DM approval relay; it does not remove their group membership or undo an earlier approval. The saved pairing list survives restart. See **Settings from chat** in [security](security.md#auto-mode-classifier).

Only the agent's primary operator may request a standing classifier approval-rule change through `/hermitd:hermit-settings rules`; other participants are told an admin must set it. A terminal operator may also request one. The native prompt still decides each edit, and a classifier `allow` cannot override native ask or deny rules.

## Participants

Groups own admission independently of the DM `allowFrom` list. Other participants should join through groups. Hermit `channels.<name>.allowed_users` narrows who can wake the hermit, never who can approve tool use: absent means accept all delivered senders, while `[]` accepts none. Removing an ID from an explicit list blocks that sender's wake eligibility; deleting the list restores accept-all. Group membership and saved allowlists survive restart. Any member of an enabled group can attempt a permission reply by guessing its code before a hermit hook sees it. See [channel configuration](config-reference.md#channels) and [known limitations](security.md#known-limitations).

A member's requested watch is saved disabled until a primary sender says yes in that chat. A no leaves it disabled.

**Recall scope.** Per-channel `isolate_chats` and `shared_chats` own channel-log visibility: own chat by default, the whole channel when isolation is false, plus listed shared chats from any configured channel. Removing a shared id removes that grant; removing `isolate_chats` restores isolation. The maintainer chat is always unscoped, and the home chat is unscoped only on a technical profile. A home chat pinned to a shared group therefore gives every member of it unscoped recall across every chat on every channel, the same standing exposure the control-command rule has — set `allowed_users` and keep the pin on a real DM to narrow it. An unknown channel sees only itself. Terminal search is unscoped. Briefs follow the recall scope of the chat they answer in and also count records in that chat's public threads. Shared-chat grants do not expand to their children; private threads are not rolled up. Briefs require `--agent`, `--chat` or `--routine`; terminal and Remote Control use `--agent`. Chat briefs list decisions on visible conversation records. Briefs to any chat other than the home chat omit null-conversation admin decisions, duties and priorities and skip upgrade checks and dashboard refresh; the home chat keeps them on every profile. Compiled pages are scoped by frontmatter `audience` (`shared` or `<key>:<chat_id>`; absent means `shared`). Session reports and proposals are operator material, unavailable to scoped readers. The resident's own context is shared across chats for non-task turns.

**Operators.** `channels.<name>.operators` names the admin for agent-wide standing roles, approval rules, watch approvals, and tool sign-in. Removing it restores the first-allowed-user rule; without `allowed_users`, the maintainer chat or technical-profile home chat qualifies. When a group is the maintainer chat or the home chat on a technical profile, and the channel has neither `operators` nor `allowed_users`, every member of it, including in its public threads, counts as admin for decisions and proposal consent; set `operators` to name the admin. Without any of these fields nobody is primary. When `operators` or `allowed_users` names people, the agent's pending questions in a chat take answers only from the admin, or from the member a question was asked of about their own request; otherwise authority follows the primary-operator rule. Chat input decisions admit allowed members of that chat, and requester decisions admit the named requester or an admin. A chat decision, close, cancel or clear-wait that names a sender is refused unless that sender's message opened or joined the current turn, so terminal and wake turns cannot name one. Proposal consent always requires an admin. Terminal and Remote Control answers use `task answer <id> --local --reply yes`, confirmed by Claude Code's permission prompt; bypass mode refuses it. Other admitted senders save roles pinned to their current chat and cannot change hermit-wide rules. This list does not own control commands or native prompt delivery, and never bypasses admission. Existing roles remain as saved.

**Chat instructions.** `channels.<name>.instructions` holds operator-set policy for individual chats, ahead of memory roles. Every add, change or removal raises the native permission prompt. Approvers are the DM-paired `allowFrom` users, not `operators`; admitted members can still save memory roles without changing these instructions.

## Control commands

Bare `!release` uses the same trusted-controller gate as pause. It releases human browser control, keeps the task claim, and reports whether anything was held. Other senders cause no state change or response.

The hermit's `isTrustedController` rule owns pause, resume, snooze, and full status authority. With `allowed_users` set, it checks the sender against that list. Without it, the rule trusts the pinned `default_chat_id`; without a matching home chat there is no trusted controller. A shared home matches every member, so use an explicit list to narrow control there. Removing a sender from a configured list removes their control authority, but removing the whole list restores the home-chat fallback. The saved list and home pin survive restart; a new inbound DM does not move the pin. This rule does not own native approval delivery. Separately, adding a listening chat through `hermit-settings channels` asks for native approval and is refused under bypass permissions. See [security limitations](security.md#known-limitations).

## Connections

Each tool uses one account for every chat and routine in the resident. Anyone admitted may ask to reconnect it, but only an admin may finish sign-in. A primary operator has this authority; when neither `operators` nor `allowed_users` names people, the trusted pinned home chat can finish. Explicit empty lists grant nobody authority. Someone typing at the terminal can also finish it; a turn nobody typed, such as a routine, a peer wake or a background helper, raises the native permission prompt, and so does any turn such a wake or another sender joins midway. Prefer a dedicated account and forward the sign-in link if someone else owns the tool account. Different access requires separately configured residents.

Native settings own project MCP enrollment through `enabledMcpjsonServers`, `enableAllProjectMcpServers`, and `disabledMcpjsonServers`. Without approval, a project server stays pending without blocking boot. Remove approvals in every applicable native scope, including blanket approval, or explicitly disable the server to exclude it at restart. Removing enrollment does not delete its declaration or credentials. A temporary `/mcp` toggle does not remove the saved approval.

Native `disableClaudeAiConnectors` owns account connector loading. When unset, a login-authenticated hermit loads account connectors; setting it to `true` disables them for the project without deleting account connections. Removing the setting restores default loading at restart. Setup-token authentication fetches no account connectors. See [MCP servers](always-on.md#mcp-servers).

## Browser phone takeover

Managed browsers on Docker and hosts work without takeover setup for public pages. Phone sign-in is opt-in: `/hermitd:browser` collects a short `browser.admins` list in chat through the native-prompt settings route, asks for one host `hermitd run browser-host` command, verifies it, and declares one `browser-handback` stream monitor. Existing hermits receive the browser through upgrade; viewer access remains opt-in.

Takeover needs Tailscale. Docker also needs server 28.0.0 or newer and an image whose `/etc/hermit/managed-browser` marker contains `display=plugin`. The plugin owns display startup independently of the entrypoint; older bare markers require `hermitd update`. If the Dockerfile lacks the delimited managed-browser block, ask the hermit to merge its parked upstream copy first. It publishes one loopback port and uses tailnet-only Serve, never Funnel. Linux/WSL2 tmux hosts use the same command for prerequisites and display startup; macOS hosts outside Docker and interactive hermits refuse takeover; Docker Desktop host-networking loopback reachability remains unverified and a failed route check is reported. No image rebuild is needed for takeover on an image already carrying the managed browser.

Only an exact allowlisted Tailscale user login may load the viewer or its WebSocket. A tagged phone has no user identity and is refused. After checking identity, the viewer checks Host against `browser.host:browser.port`. The page checks Origin against Host for Take over, Hand back and the socket upgrade. There is no watch mode: the newest Take over wins and closes older sockets. A dropped connection keeps control until Hand back, trusted-controller `!release`, browser loss, or 30 minutes without a viewer. Anonymous headless tasks can continue during human control; signed-in tasks share one claimed profile and queue.

The login request stays in its original conversation and mentions the admin using the configured handle for that channel. Its `?task=<id>` link names the waiting task. Hand back leaves Chrome and its page running. A durable event wakes the resident; the task writer conditionally clears only the matching `waiting_since`, then the agent checks the expected page and account before continuing once. Forced release, expiry and browser loss wake it too, without claiming sign-in succeeded. The viewer never writes task records.

This checks tailnet identity, not the agent's honesty: the agent inside the container, a host process reaching loopback, or another container reaching port 6080 on the same Docker network can forge the identity header. See [known limitations](security.md#known-limitations).

## Unattended settings writes

`channel-access.ts` owns pairing, policy, delivery defaults, and group enrolment from the setup wizards and chat. Channel plugins remain writers of `access.json` too. Group changes write `config.json` first through the shared config persister, then re-read and write access state. There is a brief window between files, without a lock, journal, or rollback. If the access write fails after config lands, the command reports `{"error":"partial_config_written"}` and asks the operator to re-run the same command; it does not report complete success.

The shipped `SEALED_SETTINGS_OPS` list owns the enumerated classifier exception, rendered into a per-session overlay at each boot. An absent op has no exception from this list. Removing an overlay entry by hand does not persist across restart: boot renders it again from the installed list. The exact constraints remain in [the sealed exception](security.md#auto-mode-classifier).

Boot separately owns local settings keys and terminal-only operations, including voice rendering and artifact revocation. These run outside a session; a chat decision records config rather than executing the revoke. Unset behavior depends on the key: language clears its local mirror, voice leaves the operator's pick alone, and artifact authorization leaves an existing grant alone. Removing a generated local value is not a durable opt-out when configured boot ownership still applies.

## Preferences

Hermit `model` and `effort` are launch flags only when set. Unset values pass no override and leave native defaults in charge. Removing either override stops reasserting it at restart without deleting native settings; a configured override returns at restart after a runtime change.

Hermit `language` is carried by the resident launch overlay when configured. Clearing it leaves native preferences in charge. The native `/config` Language picker writes user scope and survives restart.

Hermit `voice.style` owns the launch overlay `outputStyle` when configured. `voice.style: null` leaves the operator's pick alone, including an existing rendered value; clearing the config is not deletion of the style or custom style file. A configured style is reasserted at restart. See [configuration](config-reference.md).

## Upgrades

Installed plugin code owns shipped permission registries; hermit config and native settings retain their existing owners through upgrades. There is no new access key or enrollment conversion. An unset preference or enrollment remains subject to its surface's defaults, not a second access registry. Permission sync removes only named obsolete rules and preserves other operator entries. Removing a canonical grant by hand can be undone by permission sync; removing a boot-owned value can be undone at restart while its config still applies. Operator-authored state survives except for explicitly documented migrations. See [security](security.md#auto-mode-classifier) for the upgrade-triggered sealed exception.

## Revocation

An explicit `artifacts.publish_authorized: false` removes exactly `Artifact` from `permissions.allow` at the next boot, preserving all other entries and keys. It clears every settings file the plugin wrote the grant to: the local one, which the boot grant re-ensures, and the committed one when `state/hatch-options.json` stamps the hatch target `committed`. An install carrying no usable stamp is cleared locally only, because an unstamped entry's provenance is unknown. An absent entry is a no-op, and costs no subprocess. A `null` decision leaves an existing entry alone. Disabling pages or switching backend alone does not revoke an existing grant; `true` re-ensures it only when a page is enabled and the backend is the default Claude backend.

Removal takes effect through the next boot, not immediately in the current session. It removes this standing permission, not previously published pages, banked URLs, account sharing, or permissions in other scopes. The declined decision survives restart and continues to enforce removal. See [artifact authorization](config-reference.md#artifacts) and [security limitations](security.md#known-limitations).

Avoid shared hosts: a local user can reach Chrome’s debugging port or forge the loopback login header. Xvnc runs without `-auth`. The Linux phone test is the manual pre-merge gate; macOS hosts and WSL2 remain unverified by a live run.
