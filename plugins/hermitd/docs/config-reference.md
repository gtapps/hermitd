# Configuration Reference

Full schema for `.hermit/config.json`. Generated by `/hermitd:hatch`, managed by `/hermitd:hermit-settings`.

## Top-Level Keys

| Key | Type | Default | Description |
|-----|------|---------|-------------|
| `_hermit_versions` | object | `{}` | Plugin version tracking. Updated by `/hermit-evolve`. |
| `agent_name` | string | `null` | Display name for the agent (e.g., "Atlas"). Optional. Also becomes the session's cross-session peer name and its Remote Control name — sanitized to `[A-Za-z0-9_-]`, falling back to the tmux session name (`hermit-<project>`) when unset. Two hermits sharing a config dir and an `agent_name` collide; `ListAgents` disambiguates them with a `[ref]` suffix. This value is the name the hermit *requests*: when another live session already holds it, Claude Code keeps the name with that session and renames this one to a variant, so the effective name is the `name` field of `<config dir>/sessions/<pid>.json` (the pid is `runtime.json`'s `session_pid`), not `peer_name`. |
| `language` | string | `null` | Preferred language for responses. Auto-detected from locale. Also applies to script-composed channel messages (budget, denial, mint, watchdog, status), not just model replies. Boot carries this value in the resident launch overlay when set. The `/config` Language picker writes user scope and survives restart. See the [access model](access-model.md#preferences). |
| `timezone` | string | `"UTC"` | IANA timezone (e.g., "Europe/Lisbon"). Auto-detected. |
| `escalation` | string | `"balanced"` | Autonomy level: `conservative`, `balanced`, `autonomous`. |
| `voice` | object | `{"style": null, "prose": null}` | How the hermit talks to you, rendered into Claude Code's `outputStyle`. See [`voice`](#voice--voice) below. |
| `operator_profile` | string | `"technical"` | Audience of the person on the primary channel: `"technical"` (the maintainer runs the box, so technical/ops/spend detail may reach the primary chat) or `"non-technical"` (a client/end-user, not the maintainer). `non-technical` forces technical alerts and spend figures to a channel's [`maintainer_channel_id`](#channels) (with no client-chat fallback when none is set) and deflects client-chat spend questions with a plain "handled by your provider" reply. It also scopes the primary chat's recall when `non-technical`. It does not decide who may change settings. See [`docs/security.md`](security.md) § Settings from chat. |
| `channels` | object | `{}` | Channel configuration keyed by channel name. See [`channels`](#channels) section. |
| `remote` | boolean | `true` | Enable Remote Control via claude.ai/code, for the resident session and for background helpers `/spawn-session` launches. When `false`, boot sets `isolatePeerMachines: true`, so cross-machine peer messages require approval. Remote Control itself only connects on a claude.ai sign-in — see `auth_mode` below. |
| `auth_mode` | string \| null | `null` | Which credential this hermit runs on: `"login"` (a claude.ai sign-in in `.credentials.json`, renewed about every 30 days from chat, and the only credential Remote Control accepts) or `"token"` (a long-lived `setup-token`, renewed about yearly from chat). `null` means nobody has said, and it is resolved from what is actually on the credential volume — a token file means `token`, a stored sign-in means `login`. Setting this records an intent only; run `/hermitd:relogin` (or `hermitd-docker login` / `hermitd-docker setup-token`) to actually sign in with the new method. Unrelated to `render-docker-templates.ts`'s compose-time `auth` input, which chooses how the container is *seeded* at build time. |
| `model` | string | `null` | Override model for Claude Code (e.g., `"sonnet"`). |
| `effort` | string \| null | `null` | Override reasoning effort, passed as `--effort` at boot (e.g. `"high"`). Re-asserted on every start, so a channel `!effort` change reverts on restart — **only when set**: at the default `null` no flag is passed, and a runtime `/effort` writes through to the user-scope default and survives restarts. Mutually exclusive in practice with `env.CLAUDE_CODE_EFFORT_LEVEL`, which pins the session and makes a runtime `/effort` do nothing. |
| `permission_mode` | string | `"auto"` | Claude Code permission mode: `default`, `acceptEdits`, `auto`, `plan`, `dontAsk`, `bypassPermissions`. `auto` (default) is generally available to all users across subscription plans and API usage; supported models and provider configuration can vary. If Claude reports it unavailable for the current selection, choose a supported model or switch via `/hermit-settings permissions`. Re-asserted on every start, so a channel `!permission-mode` change reverts on restart. See [permission modes docs](https://code.claude.com/docs/en/permission-modes). |
| `tmux_session_name` | string | `"hermit-{project}"` | tmux session name for always-on mode. |
| `auto_session` | boolean | `true` | Run resident boot initialization on launch. |
| `boot_skill` | string \| null | `null` | Overrides the default `/hermitd:resident-start` bootstrap that `hermitd-start.ts` sends into the tmux REPL on always-on launch. Set to a namespaced skill (e.g. `"/hermitd-homeassistant:ha-boot"`) to run a domain hermit's custom boot. The domain skill is responsible for calling `/hermitd:resident-start` itself. Populated automatically by `/hatch` when an activated hermit declares `hermit.boot_skill` in its `.claude-plugin/hermit-meta.json`; operators can override via `/hermit-settings boot-skill`. |
| `shutdown_skill` | string \| null | `null` | Skill sent on resident stop (`hermitd-stop`, `hermitd-docker down`, container SIGTERM) after the running turn ends. It does not confirm, cancel, or archive task records. |
| `always_on` | boolean | `false` | Set to `true` by `hermitd-start`. Affects routine framing and channel behavior. |
| `push_notifications` | boolean | `true` | If `true`, fires `PushNotification` (desktop notification, plus mobile push if Remote Control is connected) on proactive alerts when no channel is enabled, when a configured channel is unreachable (missing pairing/`dm_channel_id`, empty `allowed_users`), or as a last-resort signal if a successful resolve's reply call fails. In always-on Docker / headless tmux only the Remote Control mobile push is visible. Push is one-way — operator→hermit replies still need a channel. Toggle via `/hermit-settings push-notifications`. |
| `ask_gate` | boolean | `true` | See [`ask_gate`](#ask_gate) below. |
| `quality_gate` | object | `{"tier": "budget"}` | Post-implementation quality gate at step (e.5) of `/proposal-act`. `tier` is one of: `"budget"` (never runs `/simplify`; default), `"balanced"` (makes an inline per-implementation RUN/SKIP decision from the proposal category and touched files), `"quality"` (always runs `/simplify`). Cleanup cost depends on the native command, selected models, and target. Anything outside the enum or a missing key resolves to `budget` at runtime (default-safe). The RUN/SKIP decision itself is owned by `proposal.ts quality-gate`, which reads this key and the proposal's `category` and returns one verdict to every caller — the tiers above describe intent, the verb is the authority. Tune via `/hermit-settings quality-gate`. |
| `budget` | object | `{"daily_usd": null, "weekly_usd": null, "monthly_usd": null, "action": "alert"}` | Spend caps checked at every Stop. See [`budget`](#budget) below. |
| `telemetry_export` | object | `{"enabled": false, ...}` | Optional health/cost bundle export to a webhook. See [`telemetry_export`](#telemetry_export) below. |
| `artifacts` | object | `{"dashboard": true, "proposals": true, "weekly_review": false}` | Publish status/proposals/weekly-review pages to Claude Code Artifacts. See [`artifacts`](#artifacts) below. |
| `chrome` | boolean | `false` | Launch the resident with `--chrome` (Claude in Chrome). Ignored with a boot warning inside a container, where no browser exists. |
| `storage_drift` | object | `{"ignore": []}` | `storage_drift.ignore` lists extra top-level directories inside `.hermit/` that the storage-drift detector should not flag. |

## Settings Change History

Hermit records settings changes in the append-only `.hermit/state/settings-audit.jsonl` ledger. Each row names the changed dotted path, when it changed, and the source — an operator edit, upgrade, learned channel id, boot flip, or permissions sync. For id-keyed arrays such as `routines`, the row also names which entries and fields changed. Writes made during an upgrade are marked `upgrade:<actor>`. Credential-bearing keys and every key under `env.*` record presence only, never values. `HEARTBEAT.md` edits made through `heartbeat edit` are recorded as a fingerprint and line count (`heartbeat-edit`); hand edits are not recorded until the next chat-side edit.

Run `/hermitd:hermit-settings history [setting]` to print recent changes, optionally filtered to one setting. `/hermitd:recall` reads the same ledger when you ask questions such as "did something change my settings?"

Before applying a version's migrations, `/hermitd:hermit-evolve` snapshots `config.json` so additions and rewrites are attributed to that upgrade. If the snapshot is unavailable, the migration still succeeds and reports `Audit scope: version-only` instead of silently claiming complete attribution.

## `env` (Environment Variables)

Resolved at boot by `hermitd-start` into the resident launch overlay and process environment. Truthy ambient values win over config. Exported to hooks, MCP servers, and Bash tool calls.

| Key | Default | Purpose |
|-----|---------|---------|
| `AGENT_HOOK_PROFILE` | _(unset)_ | Hook profile: `minimal`, `standard`, `strict`. Not seeded into a new config — with nothing set, a managed (always-on/Docker) launch resolves `strict` and an interactive one `standard`. Set it here to override; an ambient value in the environment outranks it. A managed launch is floored at `standard`, so `minimal` is raised. Never written to `settings.local.json`. |
| `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE` | `"65"` | Auto-compact at this % of context window. |
| `MAX_THINKING_TOKENS` | `"10000"` | Cap on thinking tokens per turn. |
Modify with `/hermit-settings env` — except `AGENT_HOOK_PROFILE`, which that command refuses; edit `config.json` directly for it.

`*_STATE_DIR` vars are **not** stored in `env` — `hermitd-start` derives them from `channels.<name>.state_dir` at boot.

## `channels`

An assignment from chat opens a task record and runs in an internal task worker with its own context. On a Discord text or announcement channel the assignment opens a thread first; every other chat is its own thread. The record's `conversation` key is that thread, and while the record is open every message in the chat belongs to it.

| Platform | Thread ownership |
| --- | --- |
| Discord | One thread per task from a text or announcement channel; an existing thread or DM carries its own record. |
| Telegram | One record per group or DM; forum topics share the group's record. |
| iMessage | One record per chat. |
| Marketplace channel plugins | One record per chat id supplied by the plugin. |

A message in an open task thread costs one resident routing turn in addition to the worker's own work; the worker edits its own progress card, so progress costs the resident nothing. Results and progress cards use the channel plugin's reply/edit tools. `!mute`, `!unmute`, `!restart`, and `!help` apply to the task thread. Per-conversation `!model` and `!effort` are not supported.

Thread ownership lives in the task record under `tasks/`, not in a separate store. An allowed sender's messages in an open task thread bypass the passive-chat block; a muted thread admits mentions and any addressed `!` command, so `!pause`, `!status`, and the conversation commands keep working there. A chat with no open record retains its mention requirement. The upstream channel plugin must still deliver the message: Discord threads inherit the parent's mention gate and sender allowlist.

Object keyed by channel name. Built-in channels (`"discord"`, `"telegram"`, `"imessage"`) resolve their plugin from `claude-plugins-official` automatically; third-party channel plugins set the `marketplace` field below. All channel configuration lives here — no top-level `allowed_users` or `morning_brief` keys.

An inbound message's envelope carries a plugin-qualified `source` on the wire (e.g. `source="plugin:discord:discord"`), not this bare key — every hook that reads `channels` normalizes the envelope source back to it first (`lib/channel-envelope.ts`'s `normalizeChannelSource`), so config only ever needs the bare name shown here.

| Top-level key | Type | Default | Description |
|---------------|------|---------|-------------|
| `primary` | string | _(absent)_ | Preferred channel for proactive outbound sends (e.g. `"discord"`). When set and the named channel is reachable, it takes priority. When absent, the resolver returns the first eligible entry in `channels` in operator's config order — no hardcoded slug list. Must name an existing channel key. |

Per-channel keys (under `channels.<name>`):

| Key | Type | Default | Description |
|-----|------|---------|-------------|
| `enabled` | boolean | `true` | Whether this channel is active. |
| `allowed_users` | array | _(absent)_ | User ID allowlist. Absent = accept all. `[]` = accept none. Only people who may approve tool use should be DM-paired, because every `allowFrom` DM receives and can answer native permission prompts; everyone else joins through a group whose admission is independent of `allowFrom`, and `allowed_users` narrows who can wake the hermit, never who can approve. |
| `dm_channel_id` | string | `null` | Chat ID of the last inbound conversation, learned from inbound messages. Never set manually. Only a reply the hermit sends during a turn that an inbound message from that same chat opened is learned here; a proactive send (routine, heartbeat, scheduled brief) into a second chat never moves it. A `chat_id` equal to the channel's `maintainer_channel_id` is never learned here either — the maintainer chat is never adopted as the DM/control chat. Replies always go to the chat that wrote in, so this field moving is harmless — the destination for *unattended* sends is `default_chat_id`. |
| `default_chat_id` | string | `null` | **The pinned home**: destination for unattended proactive sends (briefings, notices, weekly review), and — on a channel with no `allowed_users` — the chat trusted for pause/resume/status (`isTrustedController`). Seeded once by the same hook that learns `dm_channel_id`: on first pairing it's the chat that paired, and on an install that predates this field it's the *incumbent* chat, never the one that just diverted `dm_channel_id`. **No inbound message ever moves it, whoever sends it** — so a maintenance DM, or a second allowlisted user, cannot redirect the operator's briefings. Change it with `/hermitd:hermit-settings channels` → `edit <name>` → `briefing_chat`; the write raises the native permission prompt. Resolution is `default_chat_id ?? dm_channel_id`, so an install whose migration hasn't run behaves exactly as before. Must not equal `maintainer_channel_id` (validator warns; that would pin proactive sends to the outbound-routing chat and give it control authority too). |
| `maintainer_channel_id` | string | _(absent)_ | Optional second destination (same bot/token, different chat) for technical, operational, and spend content ([security](security.md#tiered-disclosure)). Outbound routing only: it does not decide who may change settings. Tiered alerts route here; the primary chat gets plain-language client copy. Sends use the direct platform API, not `access.json`, so the bot must be present. It is not a control surface: control keywords and reauth replies stay on the primary DM chat. Set manually and verify with `/channel-setup`; a mistyped ID otherwise fails silently. |
| `bot_user_id` | string | _(absent)_ | The hermit's **own** bot account id on this platform, captured at pairing by `/channel-setup` (or backfilled by `hermit-evolve`). Three readers. It lets the reply reminder tell the model that a mention of this id is addressed to it — without it, a mention-gated channel can deliver `<@bot-id>` and the model reads it as third-party traffic. It is also what strips a leading `<@bot-id>` off a control command, so `<@bot-id> !pause` binds where a mention is required; absent the key, that whole channel's control commands silently no-op. On Discord it is also the member id in the guild-roles lookup (`GET /guilds/{guild}/members/{bot_user_id}`) that decides which `<@&role>` mentions are addressed to the hermit; absent the key that lookup is skipped and a role mention never wakes a passive chat. Never an auth input — it only ever decides which message text is addressed to the hermit, and who may actually issue a control command is still decided by `allowed_users` / the pinned home chat. Automatic capture covers Discord and Telegram; any other channel (iMessage, third-party plugins) prints a `SKIP` line instead, and setting the key by hand there gives the same behavior. Re-running `/channel-setup` refreshes it after a bot swap; `hermit-doctor` warns when it no longer matches the token's bot. |
| `bot_username` | string | _(absent)_ | The bot's own `@handle`, captured alongside `bot_user_id`. Telegram mentions carry the handle rather than the numeric id, so the self-mention match needs both. It is also what lets a control command addressed to the bot be accepted, in either form — the `!pause@handle` suffix, or a leading `@handle !pause` mention — on any channel with a stored handle, not just Telegram, though it's Telegram that produces both. Unlike the id, a handle can be reassigned — `hermit-doctor` warns when the bot has been renamed, because a stale handle stops matching (including suffixed commands, which stop working) and can start matching whoever claimed the freed name. |
| `passive_chats` | string array | _(absent, off)_ | Chats recorded for recall while waking only for mentions from allowed senders. Requires plugin `requireMention:false` and empty per-chat `allowFrom`. Telegram requires privacy mode disabled in BotFather; forum topics share the group id. Discord threads follow the listed parent; forum channels are unsupported. Denying Create Public/Private Threads is the zero-code alternative, at the cost of automatic task threads (see conversation ownership above). A listed DM id is just blocked. Authorized replies in an open task thread can wake without a mention. Elsewhere, reply-to-bot without a mention and plugin `mentionPatterns` do not wake in a passive chat, and neither do the five control commands — `<@bot-id> !pause` binds, bare `!pause` is swallowed. Needs `bot_user_id` (nothing can match a mention without it) and `allowed_users` (absent, every member who mentions the bot wakes it); `hermit-doctor` warns for both. An addressed turn includes the most recent un-mentioned messages from allowed senders since the hermit's last recorded reply in that chat (sensitive sends are never recorded, so the boundary is the log, not every platform reply) and within the last six hours; this requires channel logging to be on, and non-allowed members' rows are recorded but never injected. |
| `isolate_chats` | boolean | `true` | Channel-log `/recall` sees the asking chat by default; `false` widens to every chat on this channel only, including compiled pages whose `audience` is that channel. Listed shared chats from any channel are also visible. The maintainer chat is always unscoped; the home chat (`default_chat_id` or `dm_channel_id`) is unscoped only on a technical profile. An unknown channel stays private to its own chat. Terminal search without `--chat` is unscoped. |
| `shared_chats` | string array | `[]` | Chats on this channel whose log may be recalled by any chat on any configured channel, in addition to its own chat and any whole-channel grant. Weekly review files those chats as `audience: shared` compiled pages and to auto-memory. Sharing the maintainer chat warns. |
| `operators` | string array | _(absent)_ | Primary operator user ids for saving, updating, and forgetting hermit-wide standing roles. Not a control-command list. When unset, the first or only `allowed_users` entry is primary; without that list, the maintainer chat or technical-profile home chat qualifies. Without those fields nobody is primary. `[]` names nobody. An id outside an existing `allowed_users` list warns and does not bypass admission. |
| `log_chats` | boolean | _(inherit)_ | Overrides `knowledge.channel_log_enabled` both ways: `false` skips this channel even when global capture is on; `true` records it even when global capture is off. Omit to inherit. Existing rows remain. |
| `state_dir` | string | `.claude.local/channels/<name>` | Path to channel plugin state dir — relative to project root or absolute. `hermitd-start` resolves relative paths against `cwd`; on a bare-host boot, an omitted value uses the project-local default shown here. It derives and exports `<NAME>_STATE_DIR` at boot in either case. |
| `marketplace` | string | _(absent)_ | Marketplace name for third-party channel plugins. When set, `hermitd-start` builds `--channels plugin:<name>@<marketplace>` instead of using the built-in `claude-plugins-official` mapping. Required for any channel other than `discord`/`telegram`/`imessage`. |
| `morning_brief` | object | `null` | `{ "enabled": true, "time": "07:00" }` to deliver morning brief via this channel. |

Example:
```json
"channels": {
  "discord": {
    "enabled": true,
    "allowed_users": ["123456789012345678"],
    "dm_channel_id": "987654321098765432",
    "state_dir": ".claude.local/channels/discord",
    "morning_brief": { "enabled": true, "time": "07:00" }
  }
}
```

Manage with `/hermit-settings channels` (subcommands include `primary <name>` and `primary clear` to set/clear the primary outbound channel) and `/hermit-settings brief`.

## `heartbeat`

| Key | Type | Default | Description |
|-----|------|---------|-------------|
| `enabled` | boolean | `true` | Enable heartbeat on idle transitions. |
| `every` | string | `"30m"` | Heartbeat interval (e.g., `"15m"`, `"30m"`, `"2h"`). Quiet polls are zero-token at any cadence, so this sets how fast the damper-bypassing gates (pending proposals, budget, suppressed digest) are picked up — not how often the full checklist is re-read, which `clean_recheck_cooldown` governs. |
| `active_hours.start` | string | `"08:00"` | Start of active window (heartbeat pauses outside). |
| `active_hours.end` | string | `"23:00"` | End of active window. |
| `stale_threshold` | string | `"2h"` | Heartbeat staleness window. Validated as a duration; no current script reads it. |
| `waiting_timeout` | string/null | `null` | Waiting-state timeout. Validated as a duration when set; no current script reads it. |
| `model` | string/null | `"sonnet"` | Model for the heartbeat EVALUATE subagent (`opus`, `sonnet`, `haiku`). `null` uses the session model. |
| `clean_recheck_cooldown` | string/null | `"6h"` | After a clean EVALUATE (nothing found), suppress re-evaluation for this window. Trades up to this much latency for surfacing a newly-arising condition in exchange for ~3× fewer LLM wakes/active-day. `null` disables (reverts to per-tick EVALUATE). All time-sensitive gates — micro-proposal, pending-proposal, task-queue, suppressed-digest — bypass the damper. Bypassing it is not the same as firing forever: the micro-proposal and pending-proposal gates damp on their own `micro-proposal-pending:*` / `proposal-pending:*` suppression ladders. |

> **Note:** The tick counter (`total_ticks`) lives in `state/alert-state.json`, not here. It is runtime state, not operator configuration.

Modify with `/hermit-settings heartbeat`.

## `watchdog`

Out-of-session supervisor that detects dead or wedged sessions and restarts them. On a tmux always-on boot, `hermitd-start` registers the OS scheduler automatically (`scheduler_enabled` defaults to `true`). That first registration also sets `enabled: true`; hygiene-only (`enabled: false` with the timer installed) is still valid. Opt out with `hermitd watchdog uninstall` (removes an already-registered timer and sets both flags `false`), or with `scheduler_enabled: false` before the first boot to skip registration entirely. **Docker hermits:** `/docker-setup` sets `enabled: true` automatically at the end of setup; the entrypoint loop already runs the watchdog, so no host scheduler is needed.

| Key | Type | Default | Description |
|-----|------|---------|-------------|
| `scheduler_enabled` | boolean | `true` | Durable scheduler policy. `true` (the default, including when the key is absent) means a tmux always-on boot will register the watchdog. `false` is the operator opt-out: boot skips registration, and doctor reports "scheduler opted out" instead of telling you to install. It only blocks *re-registration* — a timer already installed keeps ticking (and keeps restarting, since `enabled` is untouched), so on an existing install run `hermitd watchdog uninstall`, which removes the unit and sets both flags `false`. `install` sets this `true`. Docker ignores it: the entrypoint loop is not an OS scheduler, so doctor still checks the tick there. Distinct from `enabled` (recovery policy) so a hygiene-only hermit can keep the timer without restarts. |
| `enabled` | boolean | `false` | Enable restart/nudge/re-arm machinery. `enabled: false` disables the wedge-detection and restart path only. `context_hygiene.clear` and `context_hygiene.compact` (see below) are scheduler-owned context-hygiene — they run on every scheduler tick regardless of this flag. |
| `stale_factor` | number | `2` | Heartbeat staleness multiplier. Session is considered stale when `now - mtime(state/.heartbeat) > max(stale_factor × heartbeat.every, wedge_floor)`. Raise it to widen the threshold past the floor; to tighten below the floor, lower `wedge_floor` instead. The same threshold also spaces repeat nudges inside one wedge episode (see `wedge_floor`), so raising this widens both. |
| `wedge_floor` | string | `"4h"` | Lower bound on the staleness threshold above, independent of `heartbeat.every`. Each nudge is a paid full-context wake, so its cadence is recovery policy rather than a multiple of the poll interval — the floor stops a short poll interval from tightening wedge detection by itself. Lower it to buy back faster detection on an install that deliberately tightened `heartbeat.every`; `"0s"` disables the floor entirely (plain `stale_factor × every`). Duration format: `"30m"`, `"4h"` — always a string, a bare `0` is read as a malformed value and settles back to the `4h` default. The resulting threshold also spaces *repeat* nudges inside one wedge episode: the first stale tick nudges immediately, and further ticks are counted but silent until the window elapses (`nudge-throttled` in `watchdog-events.jsonl`), so a wedge that never escalates costs one probe per window instead of one per scheduler tick. Setting it at or above `heartbeat.clean_recheck_cooldown + heartbeat.every` lets the monitor's own cooldown-expiry recheck refresh `state/.heartbeat` before the watchdog's paid probe would otherwise fire, at the cost of a wider gap before a silently frozen idle resident is detected. |
| `escalate_after` | integer | `3` | Number of consecutive stale watchdog cycles before escalating from nudge to restart. |
| `operator_grace` | string | `"15m"` | If `last-operator-action.json` shows activity within this window, the watchdog backs off (operator is mid-conversation). Duration format: `"15m"`, `"1h"`. |

**Decision flow (one `run` cycle):**
0. Stamp `last_run` (current UTC) into `state/watchdog-state.json` — before any gate or early exit, so it records that the scheduler/loop fired the script even when `enabled: false`. `hermit-doctor` reads this as the watchdog liveness signal (stale/missing ⇒ "enabled but not firing" when recovery is on, "scheduler isn't firing" when only hygiene needs the tick).

Pause enforcement runs next, followed by steps 1–2. Telemetry export (with a 5-second wall cap) and state backup follow step 2, before the recovery config gate. These maintenance checks run even when watchdog recovery is disabled.

Steps 1–2 are **scheduler-owned context-hygiene** — the watchdog script runs them unconditionally, before the `enabled` gate at step 3.

1. If standalone clear is enabled, a quiet/age/policy trigger is due, and the safe execution boundary and two-tick pane check pass, send `/clear`.
2. If routine-hygiene compact conditions met (see `context_hygiene.compact` below) → send `/compact`, exit.
3. If `enabled: false` → exit (restart/nudge machinery disabled).
4. Read `runtime.json`. Adopt the session's launch-env stamp first: `config_dir` is assigned onto the watchdog's own `CLAUDE_CONFIG_DIR` (reaching every later `defaultConfigDir()` call, the transcript paths, and every child it spawns), and `env_auth` records whether the *session's* environment owns the credential. On a host install the watchdog runs from a systemd unit / launchd job / cron entry carrying only `PATH`, so its own environment describes the watchdog and never the session; an absent stamp (pre-upgrade, or a hand-launched session) falls back to that environment. Then: if explicit shutdown markers are set, the runtime is interactive, or no tmux session is named → exit. Idle execution still permits alert reporting; monitor recovery requires the safe execution boundary.
5. If an active session's tmux session is gone → restart and end the tick, unless fresh shared-liveness says the process survived without tmux; in that orphan shape, alert and exit instead of starting a duplicate.
6. If a re-auth relay was spawned or remains active → exit while it owns recovery.
6a. If the pane shows an auth failure, branch on how the session authenticates. A token-mode hermit (per the stamped `config_dir`) spawns the re-auth relay; a `/login` hermit gets a `lapsed-login-detected` notice repeating daily. When `env_auth` says the session's *environment* owns the credential (an API key, a bearer token, or Bedrock/Vertex/Foundry), neither applies — there is no login to renew — so it gets its own `env-auth-failure-detected` notice on the same daily cadence and the tick stops there. Stopping is required, not incidental: the tiers below would restart the session, and a restart spawns `hermitd-start` with the watchdog's environment, which on a host unit carries no key and nothing re-derives one. The stamp clears (`env-auth-failure-recovered`) once the pane no longer shows the failure.
7. If the captured pane shows a stalled dialog, **or** the session's own entry in Claude Code's registry reads `waiting` (`via registry` in the event detail) → send one deduplicated operator alert for the episode. The registry leg is shape-independent: the harness sets `waiting` for any permission dialog, including one whose footer the pane scanner does not recognise. It needs the `session_pid` stamp; without it, only the pane is read. The registry leg suppresses the tiers below for 24h; a dialog still unanswered past that falls through to step 10 so an unattended session is reclaimed.
8. If the transcript ends with an `enqueue` that has not drained for 30 minutes while tmux is alive → send one deduplicated `session-wedged` alert for the episode.
8a. If the newest assistant record in that same transcript tail is a harness-emitted API failure (`isApiErrorMessage`, model `<synthetic>`) reporting a usage limit or a 529/500 outage → send one deduplicated `api-failure` alert for the episode. Visibility only: nothing is restarted, nudged or suppressed, because the next scheduled wake re-fires on its own once the outage clears. Auth failures are left to step 6a so one event isn't notified twice; the stamp clears when a healthy assistant record supersedes the failure.
9. If a dialog is pending → exit before any tier that sends keystrokes or restarts the session. A supervision-only (`idle`) session skips step 10's wedge nudge and pane-frozen restart, but still reaches the monitor re-arm in step 11 — a hermit rests at `idle`, so that is where a dead Monitor has to be recovered from.
10. If the heartbeat is stale and the operator is quiet and the pane is frozen for `escalate_after` cycles → restart and end the tick. Before that threshold: nudge (`/hermitd:heartbeat run`). A nudge that went over the inbox socket is re-checked against the registry on the next tick: a resident still `idle` since before the post was written never read it (refused, held, or declined), so that tick types immediately instead of waiting out the throttle window (`socket undelivered` in the event detail).
11. If heartbeat or routine Monitor registration has drifted or liveness is stale, require the safe execution boundary before recovery. A restart ends the tick, so this step does not run after one. A context clear itself never re-arms monitors.

Recovery actions and alerts — including context resets, nudges, restarts, re-arms, `stall-question-detected`, `session-wedged`, and `api-failure` — are appended to `state/watchdog-events.jsonl`. Restarts also set `runtime.json.watchdog_restart_reason`; `resident-start` announces the restart to the operator channel. Restarts the watchdog detects resume the conversation when the session id is known, no other restart happened in the previous hour, and the transcript contains a user turn; a restart requested through `hermitd-watchdog restart`, such as a login renewal, starts fresh.

**Install:** a tmux always-on boot registers the watchdog on every qualifying boot (idempotent). Manual `hermitd watchdog install` remains the doctor's repair for a stale tick or an unbaked unit PATH. systemd user timer on Linux/WSL2, LaunchAgent on macOS, cron line printed as fallback. A first registration also flips `enabled: true` and `scheduler_enabled: true`; re-running install to repair a unit leaves `enabled` as the operator set it, so a hygiene-only hermit keeps the restart tier off. The cron fallback never flips either flag — nothing was scheduled. `uninstall` removes the systemd unit or launchd plist and sets `scheduler_enabled: false` and `enabled: false`; a cron fallback must be removed manually with `crontab -e`. Docker hermits don't need `install` — the entrypoint already runs the watchdog on its own ~5 min cycle.

Modify with `/hermit-settings watchdog`.

## `ask_gate`

Single boolean. When `true` (default), a PreToolUse hook denies `AskUserQuestion` and redirects the model to send the question via the channel reply tool and queue a durable micro-proposal entry, so a spontaneous ask can't silently stall an unattended pane. The deny fires only on the **managed unattended session** (an `always_on` boot with a reachable channel, identified per-session by the `HERMIT_MANAGED` env marker `hermitd-start` sets). A terminal session (`always_on: false`), a session with no reachable channel, and — crucially — a hand-launched interactive `claude` (or `docker exec` shell) in the same project are all left untouched: without the marker they read as attended, so operator maintenance flows (`/hermit-evolve`, `/hermit-settings`, `/docker-setup`) still ask normally. See [Unattended Asks](security.md#unattended-asks) for the full taxonomy, including the watchdog's separate fail-loud check for prompts that can't be redirected this way (native permission dialogs).

```json
"ask_gate": true
```

Set to `false` to opt out entirely, or launch a one-off session with `HERMIT_ASK_GATE=off` to bypass the gate for that session only. Validated by `validate-config.ts`.

## `budget`

Optional daily/weekly/monthly USD spend caps with an enforcement action, checked at every Stop against `state/cost-index.json`. Ships inert (all caps `null`) — set at least one cap to activate. Windows are independent: set any subset. Boundaries are computed in `config.timezone` — a `daily_usd` cap resets at local midnight, `weekly_usd` at the next Monday, `monthly_usd` on the 1st.

| Key | Type | Default | Description |
|-----|------|---------|-------------|
| `daily_usd` | number \| null | `null` | Daily spend cap in USD. `null` disables the daily window. |
| `weekly_usd` | number \| null | `null` | Weekly (ISO Mon–Sun) spend cap in USD — mirrors Claude Code's own weekly usage-reset cadence, useful when the hermit runs on a Max/subscription plan. `null` disables the weekly window. |
| `monthly_usd` | number \| null | `null` | Monthly spend cap in USD — aligns with a billing cycle, useful on an API-key client box where `estimated_cost_usd` is real money. `null` disables the monthly window. |
| `action` | string | `"alert"` | `"alert"`: at 100% of any cap, write a deduped breach alert — no functional change, the operator is notified. `"pause"`: also set the binding pause flag (`reason: "budget"`), which blocks every tool except a channel reply and `PushNotification` until the breached window's boundary passes (auto-resume — no operator action needed to un-stick it). |

Every session's Stop in the folder counts toward the caps and can trip the alert or pause, background helpers included. The pause gate rides the resident launch overlay ([unattended asks](security.md#unattended-asks)), so a helper already running keeps going and keeps billing until it goes idle; stop it with `claude stop <id>`.

At **80%** of any cap, a one-time warning alert is queued (separate from the 100% breach alert — both can fire independently for the same window). Alerts are deduped per period-instance (`budget-<warn\|breach>:<daily\|weekly\|monthly>:<period-key>`), so each window/level pair notifies exactly once. When several windows breach at once under `action: "pause"`, the pause resumes at the **longest** breached window's boundary (monthly > weekly > daily) — a monthly breach must not resume at tonight's midnight only to re-trip the monthly cap moments later.

Under OAuth/subscription auth, `estimated_cost_usd` (and therefore this cap) is notional — Claude Code isn't billing per-token — but the cap still bounds a runaway loop (a misfiring routine gets stopped regardless of what the dollar figure means). On an API-key client box the figure is real money; pair `monthly_usd` with a provider-side hard limit for true belt-and-suspenders coverage — this cap is a fast, in-hermit backstop, not a replacement for one.

An unrecognized model string is still priced (so caps keep working): at the current model of the tier its name contains (`fable`, `opus`, `sonnet`, `haiku`), or at the sonnet-5 rate when it names no tier, but its cost-log line is flagged `model_unpriced: true` and surfaced by `hermit-doctor`. What is priced: base input/output rates, 5-minute and 1-hour cache writes, cache reads, and fast mode. `inference_geo: "us"` is not applied.

```json
"budget": {
  "daily_usd": 5.0,
  "weekly_usd": 25.0,
  "monthly_usd": 100.0,
  "action": "alert"
}
```

Modify with `/hermit-settings`. Validated by `validate-config.ts`.

## `telemetry_export`

Opt-in periodic export of a sanitized health/cost bundle to a webhook, sent from the watchdog tick (not a routine — it still fires while the session is wedged or dead, which is the point). Ships inert (`enabled: false`, `destination.url: null`) — this is core's second direct outward egress after `hermit-doctor`'s `channel-liveness` check, so unlike most new features it defaults off; see [`docs/security.md`](security.md#known-limitations). Absent or disabled: nothing ever leaves the box.

| Key | Type | Default | Description |
|-----|------|---------|-------------|
| `enabled` | boolean | `false` | Turn the export on. Requires `destination.url` to be set. |
| `destination.type` | string | `"webhook"` | Discriminated for future destinations (e.g. `"git"`); only `"webhook"` ships in v1. |
| `destination.url` | string \| null | `null` | HTTPS endpoint to POST the bundle to. `http://` is accepted (warns) for loopback receivers/testing, but is rejected when `destination.bearer_env` is set and the host isn't loopback — a plaintext endpoint would leak the token. |
| `destination.bearer_env` | string \| null | `"HERMIT_TELEMETRY_TOKEN"` | Name of an environment variable holding the bearer token — the token itself is never read from `config.json`, only from `process.env` at send time (same convention as channel bot tokens). |
| `interval_hours` | number | `24` | Minimum hours between successful exports. |
| `redact_operator_text` | boolean | `true` | `true` (default): only numerics/enums/counts are sent — `cost.by_source` keys that embed an operator-chosen routine id (`routine:<id>`) are collapsed into a single `routine` bucket so no operator naming leaves the box. `false`: also includes named free-text fields (doctor check detail, session task/tags, alert keys, last error, pause reason, recent watchdog event reasons) and the per-routine `by_source` keys verbatim. |

```json
"telemetry_export": {
  "enabled": true,
  "destination": { "type": "webhook", "url": "https://example.com/hermit-telemetry", "bearer_env": "HERMIT_TELEMETRY_TOKEN" },
  "interval_hours": 24,
  "redact_operator_text": true
}
```

**Bundle contract (`schema_version: 1`)** — this is the interface a future fleet-side receiver consumes, so the field list below is the actual data-flow answer, not just documentation:

```
schema_version, ts,
hermit: { agent_name, versions },
doctor: { ts, checks: [{ id, status }] } | null,
cost: { today, this_month, all_time: { total_cost_usd, total_tokens, total_sessions }, by_source } | null,
alerts: { active, suppressed, total_ticks } | null,
session: { id, status, date, duration, cost_usd, tokens, escalation, closed_via, proposals_created_count } | null,
runtime: { runtime_mode, paused, paused_until, watchdog: { last_run, events_last_24h } }
```

A source that's missing or unreadable on disk becomes `null` for its section — the bundle assembler never crashes on partial state.

**Retry and failure handling:** on failure the bundle is spooled to `state/telemetry/spool/` (newest 7 retained) and retried on the next due tick; a run that's still failing waits at least 15 minutes between retries regardless of `interval_hours`, so a dead endpoint can't add a timeout to every scheduler tick. After 3 consecutive failures a deduped `telemetry:export-failed` alert is raised (cleared automatically on the next success, which also drains the spool oldest-first). None of this blocks anything else the watchdog does.

**Privacy:** the destination is *your* endpoint — this is operator-directed egress (a fleet dashboard, your own monitoring), never a phone-home to the plugin authors. Even fully redacted, the bundle is behavioral metadata: spend, session cadence, when-active, health. If you run this hermit on a **client project** (consultant/agency), be aware that exported cost/session figures can reveal that client's billing patterns even with `redact_operator_text: true` — point the webhook only at an endpoint you control, and prefer keeping redaction on.

Modify with `/hermit-settings`. Validated by `validate-config.ts`. Manual export/debugging: `bun scripts/report-export.ts [hermit-dir] [--print]` (`--print` builds the bundle to stdout without sending or stamping state).

## `backup`

Scheduled git snapshot of the hermit's own state, driven by the watchdog tick with no model turn. Default **off**: it needs a destination and a credential the plugin cannot supply, which is the documented exception to the research-preview default-on rule. Full guide in [`docs/backup.md`](backup.md).

```json
"backup": {
  "enabled": false,
  "mode": "workspace",
  "schedule": "0 3 * * *",
  "remote": null,
  "push": true,
  "include": []
}
```

| Key | Meaning |
|---|---|
| `enabled` | Master switch. Off until `backup setup` runs. |
| `mode` | `workspace` commits the project repo itself (dedicated hermit repos); `mirror` copies the hermit's files into a separate repo under the Claude config dir, leaving a host project repo untouched. |
| `schedule` | 5-field cron, evaluated in `timezone`. Plain cron semantics: windows missed during downtime are skipped, never caught up, and there is no retry between windows. |
| `remote` | Push destination. `https://`, `git@host:path`, `ssh://` (converted to https — the Docker image has no ssh client), `file://`, or an absolute path. `null` means commit locally only. |
| `push` | Whether to push at all. `false` keeps snapshots on the box. |
| `include` | Optional extras. Only `"transcripts"` is recognized; auto-memory is always included. |

The backup never runs `pull`, `fetch`, `rebase`, `merge`, `reset`, `push --force` or `--no-verify`, and never edits the repository's remote configuration — the push target is passed as an explicit URL each time. A diverged remote is reported for you to reconcile, never resolved automatically.

Secret-shaped paths, the channel log, oversized files and nested repositories are refused per path; see [`docs/backup.md`](backup.md) for the list and its limits. Push credentials come from `HERMIT_BACKUP_TOKEN`, then `GH_TOKEN`, then a `HERMIT_BACKUP_TOKEN=` line in the project-root `.env` — never from `config.json`.

Configure with `hermitd run backup setup` from a terminal. Every `backup.*` key is on the settings gate's ask list (a write raises the native permission prompt), and setup itself is not reachable from chat: a remote set from content the hermit merely read would be a standing exfiltration path.

## `artifacts`

Publishing of hermit-generated pages to Claude Code's [Artifacts](https://code.claude.com/docs/en/artifacts) feature — private `claude.ai/code/artifact/<uuid>` pages, refreshed in place from the main session. Default **on** per the plugin's research-preview feature-defaults rule (publish rides Claude Code's own governed path — org admin toggle, RBAC, retention, audit log — not a hermit-authored egress). See `docs/artifacts.md` for the full refresh protocol; this section covers the config and privacy/entitlement surface.

| Key | Type | Default | Description |
|-----|------|---------|-------------|
| `dashboard` | boolean | `true` | Publish the Hermit Dashboard (status, latest brief, proposal queue, weekly evolution, compiled-docs index), refreshed by `brief`, `weekly-review`, `proposal-create`, and `proposal-act`. |
| `proposals` | boolean | `true` | Publish the full text of open proposals, refreshed by `proposal-create` and `proposal-act`. |
| `weekly_review` | boolean | `false` | Publish the latest compiled weekly review as a stable-URL page, refreshed by `weekly-review`. Off by default because the dashboard's weekly card already carries the full review. |
| `publish_authorized` | boolean \| `null` | `null` | Whether unattended sessions may publish without a permission prompt. `null` = undecided (leaves an existing entry alone), `true` = authorized (grant applied at next boot), `false` = declined (the entry is removed at the next boot from every settings file the plugin wrote it to — the local one always, the committed one when the hatch target is stamped `committed` — not in-session; attended banking instead). See below. Set via `/hermit-settings artifact-authorization`, never edited directly. |
| `backend` | string | `"claude"` | Where pages publish. `"claude"` is Claude Code's native Artifacts. Any other value names a connected MCP artifact server. See below. |

```json
"artifacts": {
  "dashboard": true,
  "proposals": true,
  "weekly_review": false,
  "publish_authorized": null,
  "backend": "claude"
}
```

**Alternative backend:** setting `backend` to anything other than `"claude"` routes publishing to a connected MCP artifact server instead of claude.ai. The value is that server's name as Claude Code knows it. Setup is entirely yours and entirely manual: register the server, mint its token, and grant its tool permissions yourself; the hermit neither performs nor verifies any of that. A native `Artifact` publish on that backend is denied by the plugin's `PreToolUse` hook (`scripts/artifact-backend-guard.ts`), which names the backend in its reason; the tool and its design skills stay available. `hermitd-start`'s boot-time grant still covers only the native `Artifact` tool and is skipped once `backend` is not `"claude"` (it can't grant your server's tools). Once set, the hermit follows that server's own MCP `instructions` for how to publish (see [`docs/artifacts.md`](artifacts.md) § Non-claude backend deviations); the plugin hardcodes nothing about any particular server. If the server is unreachable or a call fails, the publish is **skipped**, not retried against claude.ai; a `state/artifacts.json` entry records which backend minted its URL, so switching backends never redeploys a page against the wrong host. Two things worth checking before you choose one: the pages are large (the dashboard and proposals pages run well over 100 KB and grow with your proposal queue), and the HTML they render is a fragment without a `<!doctype>` wrapper; a backend that wraps content itself handles this, one that serves HTML verbatim may render it in quirks mode.

**Requirements and fallback:** publishing needs a `/login`-authenticated session (API-key/gateway-token/cloud-provider sessions can't publish) with Artifacts entitled — available on Pro, Max, Team, and Enterprise plans, off by default in the Agent SDK/GitHub Action/MCP-server contexts and when `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC` is set. There is no reliable pre-check, so the hermit just tries to publish and falls back silently to the existing markdown-only channel delivery on any failure — flip a flag on and off freely, nothing else changes.

**Unattended publish authorization:** an unattended session can't answer the first-publish permission ask (a headless "ask" is an effective deny) — and on a `permission_mode: auto` hermit, an agent can't even grant that permission to itself in-session, because the auto-mode classifier's `[Self-Modification]` rule blocks a self-widened `permissions.allow` unless the operator's own live message requested it (see `docs/security.md` § Auto-mode Classifier). So `artifacts.publish_authorized` only ever records the *decision*: attended, `hatch`/`hermit-evolve` ask the operator and set it directly; unattended, `hermit-evolve` defers to the channel and the reply (via `/hermit-settings artifact-authorization`) sets the flag, nothing else. The actual `permissions.allow`/`autoMode.allow` write happens separately — attended, in the same breath as setting the flag; for a channel-resolved `true`, at `hermitd-start`'s next boot, run as a plain OS process outside the classifier entirely. Re-ensured every boot while the flag is `true`, so a hand-wiped entry heals itself. Declining banks the first publish of each enabled page inline during the attended setup session instead, so every later refresh is a prompt-free same-URL republish. With the flag `null`/`false` and no banked URL, unattended publishes silently no-op — a deliberate choice, not a bug.

**On-demand publish:** any compiled doc or open proposal can be published as a one-off page on operator request ("open <doc> as a page") — no config key gates this; it's operator-initiated by definition. The dashboard's compiled-docs index lists what's available to ask for.

**Privacy:** on Pro/Max, an artifact is private to your account — only you can view it, even in a shared channel. Team/Enterprise plans can additionally grant **Share** to specific org members or the whole org from the page header; sharing never crosses an organization boundary. Each published page is a rendered snapshot of hermit state (cost, proposal titles/bodies, session status, and — for the dashboard's latest-brief section — the model-composed brief text) — treat it like any other operator-facing report.

**Disabling artifacts at the Claude Code level** (independent of these flags) — any of: `"disableArtifact": true` in `settings.json`, `CLAUDE_CODE_DISABLE_ARTIFACT=1`, or adding `Artifact` to `permissions.deny`. With any of these set, publish attempts fail and the hermit falls back the same way as a missing entitlement. If you run the hermit in tmux/headless (the norm for `hermitd-start`), also set `CLAUDE_CODE_ARTIFACT_AUTO_OPEN=0` in `config.env` — otherwise a successful publish tries to open a browser with nothing to receive it.

Modify with `/hermit-settings artifact-dashboard`, `artifact-proposals`, `artifact-weekly-review`, or `artifact-authorization`. Validated by `validate-config.ts`. Renderers: `scripts/lib/dashboard.ts`, `scripts/lib/proposals-page.ts`, `scripts/lib/weekly-artifact.ts` (via `scripts/artifact.ts render weekly`) (all deterministic — no model authorship except the dashboard's embedded brief text — so a refresh costs a render, not a generation).

## `context_hygiene`

Context resets are independent of task closure. A record remains open across `/clear`, `/compact` and a resident restart until it is checked, confirmed or cancelled.

### Standalone clear

| Full field path | Type | Default | Description |
|-----|------|---------|-------------|
| `context_hygiene.clear.enabled` | boolean | `true` | Enable the standalone clear rule. |
| `context_hygiene.clear.quiet` | duration string | `"1h"` | Operator quiet duration that makes a clear eligible. |
| `context_hygiene.clear.max_age` | duration string | `"24h"` | Age since the last context reset that makes a clear eligible. |
| `context_hygiene.clear.min_tokens` | number | `20000` | Minimum estimated compactible conversation tokens for any standalone clear. |

A policy change is also a trigger. The policy hash covers `OPERATOR.md`, `TASKS.md`, `CLAUDE.local.md`, `.claude/settings.json` and `config.json`, excluding learned `channels.*.dm_channel_id`, `channels.*.default_chat_id` and `_hermit_versions`. Missing files contribute empty content.

Every trigger requires lifecycle guards, `execution.json` idle for at least 60 seconds with matching runtime identity, no running task worker, and an idle or shell registry entry when present. The pane must remain unchanged across two ticks and the token floor must be met. The fire takes the lifecycle lock, stamps the context reset, sends `/clear`, and records the policy hash and `clear:<reason>` trigger in `state/context-clear.json`. The same reason recorded for the current reset does not fire again. It creates no model wake and does not re-arm native monitors.

### Routine compaction

| Full field path | Type | Default | Description |
|-----|------|---------|-------------|
| `context_hygiene.compact.enabled` | boolean | `true` | Enable routine summarizing compaction. |
| `context_hygiene.compact.min_context_tokens` | number | `100000` | Compactible-conversation threshold after subtracting the recorded fixed context surface. |
| `context_hygiene.compact.min_interval` | duration string | `"4h"` | Minimum interval between routine compactions. |

Measured across seven installs from 2026-09-10 to 2026-09-24, the tier fired 6 to 20 times per install-week, and the first wake after a fire carried a median 77k to 120k fewer prompt tokens. 146 of 148 in-session context reductions came from this tier; native autocompact (pinned at 65% of the window) never fired below its ceiling.

Routine compaction keeps its own quiescence, operator-quiet and token guards, and has a hard 60,000-token floor. Context size uses the peak prompt tokens for one API call, not the sum of every call in a turn. A clear discards the conversation; compaction summarizes it. Neither closes task records.

Ask the hermit to change a full field path, for example: "Set context_hygiene.clear.quiet to 2h." The existing `/hermit-settings watchdog` route covers context hygiene.

## Routines

Monitor scheduling applies one global lateness limit to all scheduled routines. After downtime, the latest missed occurrence runs only if it is within `routine_max_lateness_minutes` of the current minute. Exactly the limit remains eligible; older occurrences are consumed as `skipped-late` before prechecks or model wakes. Missed occurrences still collapse into one run per routine within the existing 24-hour search window. Time an occurrence spends deferred by an open operator turn does not count toward lateness, so it fires at the first poll after the turn clears; an occurrence already past the limit when the turn opens, or one whose deferral was interrupted by downtime, is still skipped. Pause skips retain precedence. This is a dispatch-time check, not a deadline on already dispatched work.

The default is 60 minutes, including existing installations that omit the setting. For example, a 09:00 routine can run at 10:00 but is skipped at 10:01. A skipped weekly routine waits until its next scheduled occurrence. Set the limit to 1440 to retain the previous catch-up window. No config rewrite is needed to adopt the default, and operator-configured values are preserved on upgrade.

The limit requires Monitor scheduling. CronCreate fallback warns during registration that it cannot enforce the limit. The `heartbeat-restart` re-arm anchor is unaffected.

| Key | Type | Default | Description |
|-----|------|---------|-------------|
| `routine_max_lateness_minutes` | integer | `60` | Global dispatch lateness limit in minutes, 1–1440 inclusive. Monitor scheduling only; no per-routine overrides. |
| `routines` | array | `[]` | Scheduled routines. Each entry: `{id, schedule, skill, reflect_after?, model?, expect_artifact?, precheck?, precheck_timeout_s?, enabled}`. `schedule` is a 5-field cron expression (`minute hour dom month dow`) interpreted in `config.timezone`. Where the Monitor tool is available, every enabled routine except `id: "heartbeat-restart"` runs from one native plugin monitor started by the activation skill that evaluates schedules directly in `config.timezone` ; a skipped fire costs zero model tokens. `heartbeat-restart` always registers as a CronCreate re-arm anchor; the whole set falls back to per-routine CronCreates where Monitor is unavailable. `model` (optional, one of `opus`/`sonnet`/`haiku`) runs the skill in a subagent at that model to save cost on lightweight routines; omit to use the session model. Subagents run in isolated context and return only a one-line status ; only use `model` on stateless routines (not ones whose primary value is chat/transcript output). Ignored on `heartbeat-restart`. `expect_artifact` (optional) declares the exact file the routine must produce, relative to `.hermit/` ; `raw/<name>` or `compiled/<name>`, with at most one `{date}` token expanded to `YYYY-MM-DD` in `config.timezone` at fire start. Globs are rejected. When set, the fire is only recorded as `fired` if that file changed during the run; otherwise the ledger records `failed-artifact-missing` / `failed-artifact-unchanged` / `failed-verification-error` and the operator is notified. Opt-in per routine: core cannot infer what a project-level skill writes. **Most routines should not set it** ; it fits only a single file at a path known before the run and written every run; routines whose value is chat output, or whose output is variable or runtime-named, should leave it unset (see [Routine Authoring](routine-authoring.md)). `precheck` (optional) is the routine's wake gate: one of the builtins `"reflect"`, `"doctor"`, `"later"`, or a project-relative path to an executable. `"doctor"` and `"later"` ship wired on the `doctor` and `later-check` routines by default ; all are pure verdict checks with no model involvement, so a gate run costs the same as the check itself. The routine monitor runs it at fire time, before waking the session; a first stdout line of `SKIP` consumes the fire and records `skipped-precheck` at zero token cost, while `WAKE`, a non-zero exit, unparseable output, or the timeout all fire the routine as an ungated one would (failures record `precheck-error` with the reason, surfaced by the `routine-precheck` doctor check). The script gets `HERMIT_DIR`, `ROUTINE_ID` and `ROUTINE_LAST_FIRED` in a minimal environment, must be read-only, and hands nothing to the skill ; no gate output reaches the session. In CronCreate fallback mode the gate runs after the wake: same behavior, no saving. `precheck_timeout_s` (optional, default 30, max 300) bounds one gate run. A chat-side gate write raises the native permission prompt; see [`docs/security.md`](security.md) § Settings from chat. |
| `monitors` | array | `[]` | Declared background watches. Each entry: `{id, description, command, class?, persistent?, enabled, timeout_ms?}`. Auto-registered at session start via `/watch start`. `class` is `"stream"` or `"poll"` (documentation label only). `persistent?` is accepted but ignored. Watches use a deadline capped at 1800000ms and renew by task id on expiry. Runtime state in `state/monitors.runtime.json`. |
| `routine_wake_lint` | object | `{"max_windows": 6}` | Wake-clustering lint, CronCreate anchor/fallback mode only (routines due in the same monitor poll already batch into one wake — nothing to lint there). On every `/hermitd:hermit-routines load`, enabled routines' (timezone-shifted) fire-times are bucketed into 30-min windows; when they spread across more than `max_windows` distinct windows, `load` logs one advisory `WARN` line naming the loneliest fires. A wake-count nudge (fewer distinct wake windows ≈ fewer cache-cold wakes); advisory only, never blocks registration. See [Staggering routines](#cron-schedule-rules) below. |
| `doctor` | object | `{"routine_cost_floor_usd": 2}` | Tunables for `/hermitd:hermit-doctor` checks. `routine_cost_floor_usd` (default 2) is the absolute `$/run` floor for the `routine-cost` check: a routine is flagged only when its per-run cost exceeds both 3× the peer median (the other routines' median) and this floor, so cheap routines that are merely relative outliers stay quiet. Raise it to suppress low-dollar noise; lower it to catch smaller regressions. |

Modify with `/hermit-settings routines`.

### Cron schedule rules

The `schedule` field uses standard 5-field cron syntax: `minute hour dom month dow`.

| Field | Range | Notes |
|-------|-------|-------|
| minute | 0–59 | |
| hour | 0–23 | |
| dom | 1–31 | day of month |
| month | 1–12 | |
| dow | 0–7 | day of week (0 and 7 = Sunday) |

Atoms: `*` (any), exact value, comma-separated list (`1,15`), range (`9-17`), step (`*/15`, `0-30/10`). Named days/months and macros (`@daily`) are not supported. Both DOM and DOW non-`*` in the same expression is rejected (ambiguous semantics). Leading zeros are allowed (`09` = `9`). Step base `0` is invalid (`*/0`).

**Monitor mode** evaluates each routine's `schedule` directly against `config.timezone` — no shift needed, so none of the shift caveats below apply to it.

**CronCreate anchor and fallback mode** shift each routine's `schedule` from `config.timezone` to the machine's local timezone before registering — CronCreate only knows machine local time. This happens at session start and on every `/hermitd:hermit-routines load`. The shift handles minute-granularity offsets, so half-hour and 45-minute IANA zones (Asia/Kolkata, Australia/Adelaide, Asia/Kathmandu) work correctly. DOW is shifted automatically when a day-wrap occurs.

DST transitions self-correct within 24h via the daily `heartbeat-restart` reload. **On the DST transition day itself, one CronCreate-mode fire may land at the wrong wall-clock hour.** Monitor mode evaluates schedules in `config.timezone` directly and fires once across a DST transition: a schedule inside the skipped spring-forward interval fires one hour later that day, and a repeated fall-back minute fires on its first occurrence only. If your `config.timezone` is null, schedules pass through unchanged (machine-local time used as-is).

Schedules that cannot be expressed as a single CronCreate after shifting are passed through unchanged with a warning: mixed day-wrap on restricted-DOW schedules, and hour step patterns (`*/7`) that lose their structure. Avoid these in routines when `config.timezone` differs from the machine TZ; split into separate fixed-time entries instead.

**Clustering and staggering routines.** In Monitor mode, routines due in the same poll batch share one wake, so exact co-scheduling is cheapest when they can run together. Offset routines you want as separate turns by a few minutes to keep each fire inside the prompt-cache window. In CronCreate fallback/anchor mode, co-scheduled routines fire as separate idle turns; the same small stagger lets later turns reuse warm context. The defaults stagger daily `reflect` at `0 9` and weekly `hermit-doctor` at `10 9`. Plugin checks are ordinary routines with their own cron schedules.

Beyond that intra-cluster stagger, the number of *distinct* times of day the hermit wakes also matters — each cache-cold wake re-warms the whole context. `hermit-routines load` lints this: when enabled routines spread across more than `routine_wake_lint.max_windows` (default 6) distinct 30-min windows, it logs one advisory line naming the loneliest fire-times so you can consolidate them into fewer wake windows. Every-hour routines (hour field `*`, `*/1`, or `0-23`) are excluded, since they wake continuously by design.

## `reflection`

Optional. Tunes how the self-improvement pipeline graduates patterns from the observations ledger.

| Key | Type | Default | Description |
|-----|------|---------|-------------|
| `graduation_min_sessions` | integer | `1` | Minimum number of distinct sessions a pattern must appear in before it graduates from `state/observations.jsonl` to a proposal candidate. 1 = surfaces after the first session (default); 2 = requires recurrence across two separate sessions (pre-v1.2.6 behavior). |

```json
"reflection": {
  "graduation_min_sessions": 1
}
```

At `1`, a ledger candidate graduates on its first sighting — the three-condition rule's cross-session *recurrence* (condition 1) is satisfied by the ledger entry itself, while *meaningful consequence* and *operator-actionable* still gate through triage and the judge. Structural drift (`storage-drift:*`, `schema-drift:*`) is recorded once per occurrence rather than once per session, so it graduates only at `1`; set `2` to suppress single-sighting drift proposals while still graduating genuinely recurring behavioral patterns.

Set to `2` if the operator channel gets noisy. Applies to both the observations-ledger graduation gate and the procedure-capture recurrence bar. Validated by `validate-config.ts` when present. Modify with `/hermit-settings reflection`.

## Voice — `voice`

How the hermit talks to you is a config setting, rendered into a native Claude Code [output style](https://code.claude.com/docs/en/output-styles). The style reaches the **system prompt** at session start, which is why it holds for a whole session and survives compaction, where startup context fades.

```json
"voice": { "style": "Concise", "prose": null }
```

| `style` | What you get | File on disk |
|---|---|---|
| `null` (default) | The hermit doesn't own the key. Whatever you picked in `/config` — including styles the hermit doesn't render, like `Explanatory` — stays yours; the hermit only reports it. | none |
| `"default"` | Claude Code's Default style. Lowercase: the `/config` picker displays "Default" but persists the lowercase literal. | none |
| `"Concise"` | Leads with the result, skips narration, keeps error and security detail in full. | none |
| `"custom"` | `prose` — your own words — becomes the voice. Requires a non-empty `prose`. | `.claude/output-styles/hermit-voice.md`, rendered from `prose` |

Change it with `/hermitd:hermit-settings voice`, from a terminal or from your chat. The style name is an everyday setting; custom prose raises the native permission prompt (it becomes every future session's system prompt).

Notes:

- **`config.json` is the truth; the rest is its render.** `hermitd-start` writes `outputStyle` into the launch overlay; `apply-settings.ts voice-render` renders the style file for `custom` — at hatch, when you change the voice from a terminal, and at every boot. Edit `voice.prose`, not the rendered file: a hand-edit there is overwritten at the next restart.
- **Resident launch scope.** Only sessions started through `hermitd-start` receive the voice selection. The rendered style file remains gitignored.
- **Changes apply at the next hermitd-start.** The launcher renders the settings overlay for that resident session.
- **An unset voice is left alone.** Neither hatch nor boot reclaims a key you set yourself; `hermit-doctor`'s `voice-carrier` check reports what's persisted and flags only a real mismatch with `config.voice`.
- **The rendered voice file is gitignored**, so it doesn't travel with a clone (it's in `.worktreeinclude`). Migrating `config.json` is enough on its own: the next boot re-renders it.
- **Tone only.** Project focus, constraints and approvals stay in `OPERATOR.md`; channel routing rules ship with the plugin.

## Environment Variable Flow

```
config.json "env"  ->  hermitd-start.ts  ->  launch overlay "env"  ->  Claude Code  ->  hooks, Bash
                   ->  shell env (tmux temp file / Docker environment:)  ->  MCP servers
```

- **Shell env only, as far as the hermit is concerned:** `CLAUDE_CONFIG_DIR`, `ANTHROPIC_API_KEY` (OAuth credentials live in `.credentials.json`, written by `claude /login`). Claude Code stopped reading `CLAUDE_CONFIG_DIR` from *project* settings in 2.1.251, which is the scope `settings.local.json` occupies, so shell env is the only carrier `hermitd-start` has for it.
  - **But Claude Code also honors it from your own user or managed settings' `env` block**, and a value set there re-points `.credentials.json`, sessions, plugins and hooks without ever passing through the launcher's environment. `hermitd-start` cannot see it, so nothing outside the session can infer it. That is why the `SessionStart` hook stamps the resolved value into `state/runtime.json` as `config_dir` — the watchdog, which runs from a systemd unit or cron entry carrying only `PATH`, adopts the stamp instead of guessing from its own environment.
- **Launch overlay and process env:** all `config.env` keys except `AGENT_HOOK_PROFILE`, including `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE` and `MAX_THINKING_TOKENS`.
- **Process env only (never persisted):** `AGENT_HOOK_PROFILE` — resolved per launch and delivered via the tmux env file or Docker compose `environment:`, and stripped from `settings.local.json` so an interactive `claude` in the same project never inherits the managed session's profile
- **Derived at boot:** `DISCORD_STATE_DIR`, `TELEGRAM_STATE_DIR` — injected into shell env (tmux forward) and the launch overlay by `hermitd-start`, from `channels.<name>.state_dir` or, on a bare-host boot when that key is absent, `.claude.local/channels/<name>`
