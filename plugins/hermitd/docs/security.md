# Security

Safety model for autonomous hermit agents: seeded permission rules, defense in depth, and operational recommendations.

---

> **Important:** Seeded permission rules are blocklist-based string matches. They block (or prompt on) known dangerous commands but cannot prevent all harmful invocations. The default `auto` mode reduces (but does not eliminate) the need for container isolation by requiring classifier review of each action. Auto mode is generally available to all users across subscription plans and API usage; current Claude Code version, model, provider, and administrator settings can still affect availability. If it is unavailable for the current selection, choose a supported model or another permission mode. Always use container isolation when running with `bypassPermissions`. See [Known Limitations](#known-limitations) below.

## Seeded permission rules

Native Claude Code `permissions.deny` / `permissions.ask` entries, seeded once at hatch (or `/docker-setup`) from `state-templates/deny-patterns.json`. Claude Code's engine owns runtime (deny > ask > allow). After the seed, the operator owns the settings file: evolve may add ask entries additively and never removes anything; nothing re-applies or reconciles on boot.

Hatch Step 9 offers three tiers:

| Tier | What it writes |
| --- | --- |
| **Standard** (default) | `deny` into `permissions.deny`, `ask` into `permissions.ask` |
| **Hardened** | both arrays into `permissions.deny` (everything hard-blocked: client-facing / prompt-averse) |
| **Skip** | nothing seeded. Add later by editing the settings file, or run `apply-settings.ts <file> deny standard` from a terminal |

`permission_mode: dontAsk` turns ask entries into denies (Claude Code auto-denies anything that would have prompted). `allowManagedPermissionRulesOnly` (org-managed settings) restricts which permission rules a project file may add; a managed policy that forbids project-local rules will ignore this seed. Under `bypassPermissions` ask entries are not enforced at all; `/hermit-doctor`'s `permission-rules` check warns, and `apply-settings.ts <file> deny hardened` restores hard blocks.

Two classes (canonical source: `state-templates/deny-patterns.json`):

### Never-allowed (`permissions.deny`)

```json
{
  "permissions": {
    "deny": [
      "Bash(rm -rf *)",
      "Bash(rm -fr *)",
      "Bash(rm -r -f *)",
      "Bash(rm -f -r *)",
      "Bash(*/rm -rf *)",
      "Bash(*/rm -fr *)",
      "Bash(*/rm -r -f *)",
      "Bash(*/rm -f -r *)",
      "Bash(chmod 777*)",
      "Bash(*sudo *)",
      "Bash(*> /etc/*)",
      "Bash(curl * | bash*)",
      "Bash(wget * | bash*)",
      "Bash(env)",
      "Bash(printenv)",
      "Bash(printenv *)",
      "Bash(cat .env*)",
      "Bash(cat */.env*)",
      "Bash(cat ~/.ssh/*)",
      "Bash(cat ~/.aws/*)",
      "Bash(*$ANTHROPIC_API_KEY*)",
      "Bash(*${ANTHROPIC_API_KEY*)",
      "Bash(*$CLAUDE_CODE_OAUTH_TOKEN*)",
      "Bash(*${CLAUDE_CODE_OAUTH_TOKEN*)",
      "Bash(*$HERMIT_TELEMETRY_TOKEN*)",
      "Bash(*${HERMIT_TELEMETRY_TOKEN*)",
      "Bash(*> *.hermit/OPERATOR.md*)",
      "Bash(*>.hermit/OPERATOR.md*)",
      "Edit(//**/.claude/plugins/**)"
    ]
  }
}
```

The `Edit` entry keeps the hermit out of plugin source. Claude Code installs a plugin into two trees under `~/.claude/plugins/`: the marketplace clone (`marketplaces/<marketplace>/plugins/<plugin>/`) and the versioned cache (`cache/<marketplace>/<plugin>/<version>/`). The rule covers both, for every installed plugin, along with Claude Code's own `installed_plugins.json` bookkeeping.

Every part of the spelling carries weight:

- **`//`** anchors at the filesystem root. Claude Code anchors an unanchored pattern at the directory the settings file lives in, so the earlier single-slash spelling (`Edit(*/…/*)`) resolved under the project and matched nothing. `//**/` is also the portable form: paths are normalized to POSIX before matching, so it reaches every drive on Windows and WSL (`C:\Users\alice\…` presents as `/c/Users/alice/…`) as well as macOS and Linux. A `~/`-anchored spelling would not.
- **`.claude`** scopes the rule to a Claude Code config directory. Without it, `plugins/**` matches any project that happens to contain a `plugins/` directory (a CMS tree, a vendored build cache), and a `deny` can only be lifted from a terminal.

A contract test (`tests/apply-settings-permissions.test.ts`, `describe('sealed registries')`) fails on any sealed path rule that reads as filesystem-wide but is not: a bare `*` or `**` first segment, or a single leading `/`, without a `//` or `~/` anchor.

Reads of this plugin's own tree go the other way and are granted (`Read(//**/.claude/plugins/**/hermitd/**)`), because unattended paths like `hermit-evolve` read `reference.md` out of it. The mid-pattern `**` matches zero or more segments, so one rule covers both install trees, and `hermitd` names the plugin slot rather than the marketplace slot. A fork whose marketplace declares another name keeps the grant, and sibling plugins do not inherit it.

**If your config directory is not `~/.claude`.** Claude Code honors `CLAUDE_CONFIG_DIR`, and some operators run profile-separated installs (`~/.claude-work`, `~/.claude-personal`). These rules name `.claude` literally, so they do not cover such an install. Copy them into your own settings file with your directory substituted, keeping the `//` prefix:

```json
"deny": ["Edit(//**/.claude-work/plugins/**)"],
"allow": ["Read(//**/.claude-work/plugins/**/hermitd/**)"]
```

On Linux, Claude Code may print `Glob patterns in sandbox permission rules are not fully supported on Linux`. That warning is scoped to the sandbox filesystem boundary and does not apply to these rules, which are enforced normally.

The `rm` entries cover four flag orders (`-rf`, `-fr`, `-r -f`, `-f -r`) in both bare and path-prefixed (`/bin/rm`, `./rm`) spellings. See [Known Limitations](#known-limitations) for what the native engine does not fold.

Unanchored credential-word globs (`Bash(*API_KEY*)`, `Bash(*SECRET*)`, `Bash(*TOKEN*)`) are deliberately absent: they are trivially bypassed (case-sensitive, no quote/case folding) and block ordinary work (grepping a var name, a commit message). What replaces them is anchored on the `$` sigil, so it fires on an expansion of a live credential (`echo $ANTHROPIC_API_KEY`) and not on any mention of the name. Two spellings are listed per variable: `${VAR}` does not contain the substring `$VAR`. The braced entry stops at the variable name rather than at the closing brace, which is what makes every parameter-expansion modifier (`${VAR:-}`, `${VAR:0:8}`, `${VAR%x}`) land on the same glob. `Bash(printenv *)` sits beside the bare `printenv` entry for the same reason: naming one variable is the most natural targeted dump.

Three variables are covered, and they are the ones live in a hermit's own process: the two Claude credentials, plus `HERMIT_TELEMETRY_TOKEN` (the default `telemetry_export.destination.bearer_env`). Anything else an operator puts in `config.env` stays uncovered, and stays that way by design: `config.env` keys have no credential-safe rule to derive from (`MAX_THINKING_TOKENS` is not a secret), and a naming heuristic (`*_TOKEN`, `*_KEY`, `*_SECRET`) would reintroduce the word-glob problem this design retired. An operator who puts their own credential in `config.env`, or renames `bearer_env` away from its default, covers it the same way this list does: add the anchored `Bash(*$VAR*)` / `Bash(*${VAR*)` pair to `permissions.deny` in their own settings file.

These, like the `env`/`printenv`/`cat .env*` entries, are transcript hygiene against casual credential dumps, not a boundary. Several things still walk straight past them: indirection and length (`V=ANTHROPIC_API_KEY; echo ${!V}`, `echo ${#ANTHROPIC_API_KEY}`), `env | grep -i anthropic`, an `export VAR=sk-…` that puts the value in the transcript in the other direction, and reading the credential file by an unlisted path. The boundary is the container and the permission mode, not this list.

Upgrading does not leave the old globs behind: `permissions-sync`, which `hermit-evolve` runs on every upgrade, retires the three exact strings from `permissions.deny` in the settings file the hermit itself wrote them to. Removal is filtered by a sealed registry (`HERMIT_OBSOLETE_DENY`), never by shape, so an operator's own deny rules are structurally untouchable. Each removal is named in the evolve report; re-add it by hand if it was a deliberate choice.

### Recoverable (`permissions.ask`)

Standard seeds these as approval prompts. Hardened writes them into `permissions.deny` instead. A native ask on a channel-primary session relays to chat: Yes runs once, No is denied, a later call re-prompts. Ask rules on `Edit(...)` were probed clean (CC 2.1.252); the known Edit/Write *deny* enforcement bug does not apply to ask.

```json
{
  "permissions": {
    "ask": [
      "Bash(ssh *)",
      "Bash(docker *)",
      "Bash(kubectl *)",
      "Bash(npm publish*)",
      "Bash(git push origin main*)",
      "Bash(git push --force*)",
      "Bash(git reset --hard*)",
      "Bash(*--no-verify*)",
      "Edit(*.claude/settings.json)",
      "Edit(*.claude/settings.local.json)",
      "Edit(*.hermit/config.json)",
      "Edit(*.hermit/OPERATOR.md)",
      "Edit(*.claude/output-styles/hermit-voice.md)"
    ]
  }
}
```

**The `config.json` / settings / OPERATOR.md / voice-file guards are policy guards, not a filesystem boundary.** They keep an unattended session's *tool* writes (`Edit`, and Write via Edit coverage) on the `settings-edit` / `hatch-config` / `evolve-finalize` paths, which validate the whole config and record every change in the settings ledger. Redirects (`>`, `cp`, `tee`, `sed -i`) and a script writing through `fs` are not covered by these Edit rules; they are classifier-watched side channels, not a second permission engine. One deliberate exception: the two OPERATOR.md redirect globs in the deny list above stay hard denies — there is no sanctioned shell-redirect path into the operator-curated file, so nothing legitimate is lost by refusing outright. Every path glob needs its leading `*` so an absolute `file_path` matches.

Existing installs that hatched Hardened (or the older hardened extras) keep those five git/npm/`--no-verify` strings in `permissions.deny` until the operator edits `permissions.deny` by hand. `deny standard` is purely additive and never removes an existing deny, so no seeding path (hatch, docker-setup, evolve) can demote a Hardened install. Deny outranks ask, so that is stricter than the new default, never wider without consent.

## Defense in Depth

Allowed senders in an open task thread can steer its worker, including a task started by another allowed sender. Thread ownership separates tasks, not filesystem permissions or operator authority. The resident owns the task records and every channel send; a worker edits only the progress card it was dispatched with and never opens or closes a record. A worker runs in the resident's project checkout with the resident's own tool reach, so it is not a permission boundary.

Thread history handed to a replacement worker is background content and cannot grant permissions or widen its authority.

| Layer               | Where           | Enforcement           |
| ------------------- | --------------- | --------------------- |
| Seeded permission rules | `settings.json` | Mechanical*       |
| Bash sandbox        | `settings.json` (`sandbox.*`) | Kernel-enforced (`bwrap`); Claude Code's own native sandbox — hermit does not configure it, see [Bash Sandbox](#bash-sandbox) below |
| Agent-level rules   | `agents/*.md`   | Instruction-following |
| Hook enforcement    | `hooks.json` + resident launch overlay | Mechanical            |
| Config isolation    | Named volume    | Mechanical            |
| Container isolation | Docker/VM       | Mechanical            |
| Container hardening | docker-compose.hermit.yml | Kernel-enforced (defense in depth — `no-new-privileges` is load-bearing; cap drops + PID cap are incremental) |
| Advanced hardening (opt-in) | docker-compose.security.yml | Kernel-enforced (LAN block + DNS policy, resource bounds, sysctls — opt-in via `/docker-security`; LAN containment is the load-bearing layer here) |
| OPERATOR.md         | OPERATOR.md     | Instruction-following |

*\* **Deny rule caveat:** There are reported bugs where `Edit`/`Write` deny rules in `settings.json` are not always enforced — Claude Code has been observed editing files that match a deny pattern. Deny rules are the correct approach and best available option, but can't be treated as airtight today. For OPERATOR.md specifically, Claude Code's built-in `.claude/` directory protection adds a second layer. Combined, OPERATOR.md modification is unlikely but not impossible until Anthropic fixes deny rule enforcement.*

## Unattended Asks

A channel-primary hermit (`always_on: true`, at least one reachable channel) has no attached interactive surface: nobody is watching the tmux pane. `AskUserQuestion` and harness-rendered dialogs stall the session invisibly unless redirected. Native `permissions.ask` prompts now relay to the channel (Yes runs once, No is denied, a later call re-prompts). The taxonomy for handling this, in order of preference:

1. **Pre-authorize** — grant the permission ahead of time (`permission_mode`, seeded deny/ask rules) so the prompt never fires.
2. **Out-of-process** — resolve the decision outside the blocked turn entirely (the pause/resume keyword flow).
3. **Async approval** — bridge the question to the channel and let the answer arrive as a later message, so the turn can move on. This is the model for both binding instances below.
4. **Fail-loud** — when a prompt can't be redirected, notify the operator that something is stuck rather than silently hanging.
5. **Native bridge** — defer to a first-party mirror/answer path once Anthropic ships one, and shrink custom machinery accordingly.

Never bypass — no auto-answering a permission prompt, no sending Escape on the operator's behalf. Deciding what an unattended agent is allowed to do is always the operator's call, made in advance (config) or asynchronously (channel reply), never invented by the hermit in the moment. The narrow exception is the core mod's dispatch-scoped approval of `/model` requested by a trusted chat sender or an explicitly armed deferred switch. Approval lives only in memory, is bound to the dispatched target, and expires on completion or deadline. The mod awaits settings hooks first and preserves their deny, ask, or block decisions. A `/model` typed in the terminal still asks “Switch model?”. `/effort` and `/advisor` have no confirmation dialog. Every other native dialog remains untouched.

A permission-mode switch requested from a channel (`!permission-mode <mode>`) is governed by that same clause, and is not covered by the dialog exception above — Shift+Tab is a keybinding, not an answer to a prompt, so nothing here is being auto-confirmed on the operator's behalf. What makes it safe is the direction of travel and the guards around it: only `default`, `acceptEdits`, and `auto` can be reached from a channel, so a chat message can tighten what the session may do unattended but never widen it past what boot already allowed. `bypassPermissions` is refused outright — its terminal acknowledgement (`hermitd-start.ts`) exists precisely so that a present operator authorizes it. `plan` is refused for a different reason: it would leave the hermit unable to answer the channel it was asked from, and unable to be switched back. The cycler reads the mode off the status bar before every keystroke and stops the moment it cannot, which is also what keeps it from pressing anything while a dialog is open — the status bar is not on screen then. The switch lasts only for the session; a restart re-asserts `config.permission_mode`, so the durable answer to "what may this hermit do" stays in config where the operator set it.

`!model`, `!effort`, `!compact`, `!clear`, `!advisor`, and `!doctor` use the core mod with the same trusted-controller admission and prompt audit as before. None needs a tmux keystroke, and all but `!doctor` need no agent turn; `/compact` still pays for its summarization call. Observed outcomes are sent directly on Discord and Telegram, and relayed by the model on other platforms or after a failed send; `!doctor` replies from its own turn. A missing mod is reported by doctor, without a tmux fallback.

Claude Code saves `model`, `effortLevel`, and `advisorModel` in user-level settings, shared by sessions using that config directory. Configured model and effort boot flags re-assert the hermit's choices, but a null effort setting leaves the saved default in effect. Advisor is not re-asserted at boot and keeps adding spend until a trusted sender sends `!advisor off`. These commands are gated by `isTrustedController`; on a shared home chat without `allowed_users`, that includes every member of the chat.

`!doctor` starts Claude Code's own `/doctor` as a turn of the managed session, and that turn sends its result to the requesting chat. The mod starts it because Claude Code reserves it for explicit user invocation. Skills the model *can* invoke, `/code-review` among them, are not relayed: they reach the model as an ordinary chat message and run through the `Skill` tool, gated by the channel's `allowed_users` rather than the trusted-controller check, and with no hermit-side refusal of a review's `ultra`, `--post`, or `--comment` arguments. A chat that should not be able to start those needs an `allowed_users` allowlist on the channel.

Two binding instances exist today:

- **Hermit-owned skills (async approval, cooperative):** every core skill either carries the Step-0 channel-reply marker and routes its asks through the micro-proposal bridge, or contains no interactive ask at all — enforced by a static contract test (`tests/channel-ask-contract.test.ts`) that fails CI the moment a skill adds an unbridged ask.
- **Everything else (async approval + fail-loud, deterministic):** built-in flows, other installed plugins' skills, and spontaneous model-initiated questions are invisible to that static scan. A PreToolUse hook (`scripts/ask-gate.ts`, matcher `AskUserQuestion`) denies the call on a channel-primary session with a redirect reason that steers the model to the channel reply tool plus a durable `micro-proposals.json` entry — deny-steering behavior is probe-verified, the model does not retry the tool. The gate is loaded only through the resident's launch overlay, alongside `pause-gate`, `component-privacy`, and `permission-denied-notify`, rather than the plugin manifest. The overlay uses absolute script paths and is read at launch only; restart the resident to load a rewritten overlay. Guest, worktree, solo and `claude --bg` sessions launched without that overlay never load the four hooks. `HERMIT_MANAGED` is not a per-session identity for `claude --bg` helpers because they inherit the `claude daemon`'s environment. The scripts keep their `HERMIT_MANAGED` checks for attended boots: `hermitd-start --no-tmux` clears the marker, leaving only the pause gate active. Settings hooks depend on workspace trust, which `hermitd-start` seeds for the project before launch; `hermit-doctor` checks the configuration with `overlay-hooks`. The gate leans **allow** on any ambiguity, because a false-allow is caught by the watchdog's fail-loud check below while a false-deny would silently break the operator's flow. Prompts that can't be redirected this way (native permission dialogs, harness-rendered prompts below the tool layer) are instead caught by the watchdog, which recognizes a stalled dialog on the captured pane, pushes one deduped operator notification per episode, and — critically — suppresses its own wedge nudges and re-arm keystrokes for that pane so it never auto-answers the pending prompt. A channel whose recent sends are failing (revoked token, etc.) is not treated as a valid redirect target either — tracked via advisory `state/channel-health.json` (written by `lib/channel-send`) — so the ask falls through to the native prompt and the watchdog backstop above instead of being denied into a channel that can't deliver. Opt out globally with `ask_gate: false`, or per-session by launching with `HERMIT_ASK_GATE=off`; the watchdog check is unconditional on any `watchdog.enabled` hermit.

**Native bridge (`PermissionRequest`):** Claude Code has shipped a native permission-request bridge since 2.0.45: the [`PermissionRequest` hook](https://code.claude.com/docs/en/hooks#permissionrequest). Probed on CC 2.1.282, it fires for a PreToolUse `ask`, for `AskUserQuestion`, and for the auto-mode denial-limit fallback prompt, and never for a classifier denial; those fire `PermissionDenied`, which `permission-denied-notify.ts` already consumes. A hook decision replaces the prompt, so a `deny` would also pre-empt the channel relay that answers ask-rule and hook-ask prompts in place. The payload carries no field that distinguishes a settings-gate ask from the fallback prompt. Hermit therefore registers no `PermissionRequest` hook: the relay answers the prompts that can be answered, and the watchdog's pane, registry and queue-liveness legs cover the rest.

## Auto-mode Classifier

Claude Code's `--permission-mode auto` (the hermit's default) routes tool calls through a classifier that blocks anything it judges irreversible, destructive, or aimed outside the trusted environment — a second gate that runs after the permissions system, before a tool call executes. The live tmux probes used for the implementation ran on CC 2.1.201 with `--model sonnet`; current model/provider availability is governed by Claude Code rather than hard-coded here. Those probes settled how a hermit's own sealed settings writes interact with the classifier:

- **Tiers and resolution.** `autoMode.hard_deny` blocks unconditionally — the only way past it is an out-of-session executor (see below). `autoMode.soft_deny` (which includes the classifier's built-in `[Self-Modification]` rule — an agent widening its own `permissions.allow`) is cleared by either explicit intent in the operator's own live message, or a seeded `autoMode.allow` exception. The `ask_gate` tier above is a different mechanism entirely (a hermit-owned `PreToolUse` hook), not the classifier.
- **`autoMode` config is read only from `~/.claude/settings.json`, managed settings, or `--settings`** — never from a project settings file. Claude Code 2.1.207 dropped `.claude/settings.local.json` from that list (a repo or build step could otherwise inject its own classifier rules); committed project settings were never read. Re-probed on 2.1.239 with a sentinel rule and `claude auto-mode config`: user scope and `--settings` show it, both project files do not. The misplacement is silent and the settings JSON Schema doesn't mark the key user-only — upstream [anthropics/claude-code#87545](https://github.com/anthropics/claude-code/issues/87545). A hermit therefore ships its policy **per session**: `hermitd-start` renders `.hermit/state/claude-settings.overlay.json` (atomic tmp+rename, rebuilt every boot, entries sealed in `lib/settings/automode-entries.ts`) and launches with `--settings <overlay>`. Nothing is written to the operator's user settings: one project's policy must not follow them into every other Claude session, and with no cross-project locking two hermits booting could clobber each other's merge. The exclusion is `autoMode`-specific, which is why the neighbouring `skillOverrides` kill-switch below sits in `.claude/settings.local.json` instead: only keys the classifier reads need the overlay.
- **`/auto-mode-setup` is turned off in every hermit session.** Once auto mode has blocked several actions and the session still has no `autoMode.environment` entries, Claude Code offers to run it in a dialog at the end of a turn ([auto-mode config](https://code.claude.com/docs/en/auto-mode-config)). A modal on an unattended hermit blocks every inbound prompt until the watchdog restarts it, and there is no settings key for "keep the command, drop the offer" — **Don't show again** is a button in that same unanswerable dialog. So `writeSettingsEnv` seeds `skillOverrides: {"auto-mode-setup": "off"}` into `.claude/settings.local.json`, which turns off the command and the offer together. Probed on 2.1.261 in both scopes: with the key set, the command leaves the `/` menu and invoking it returns `Skill "auto-mode-setup" is disabled via skillOverrides`. Project scope is deliberate over the overlay — it also covers the sessions the overlay never reaches (a manual `claude --resume`, a `docker exec` attach, a guest session in the same directory), which meet the same dialog. Boot writes the key only when it is **absent**: no settings scope outranks this file except `--settings` and managed settings, so leaving an operator's own value alone is the only opt-out that exists.
- **Auto mode suspends wildcarded-interpreter allow rules.** Every `Bash(bun */scripts/*.ts*)` rule in the hermit's sealed allow-list (seeded by `permissions-sync`) is wildcarded, so under auto mode all of them re-enter the classifier. The literal-path resolver exceptions include: `Bash(.hermit/bin/hermitd-run channel-send *)`, `Bash(.hermit/bin/hermitd-run observations observe *)`, `Bash(.hermit/bin/hermitd-run task note *)`, `Bash(.hermit/bin/hermitd-run task list *)`, `Bash(.hermit/bin/hermitd-run backup run*)`, `Bash(.hermit/bin/hermitd-run backup status*)`, `Bash(.hermit/bin/hermitd-run later list *)`, `Bash(.hermit/bin/hermitd-run later cancel *)`, `Bash(.hermit/bin/hermitd-run later verdict *)`, `Bash(.hermit/bin/hermitd-run later due *)`, and the four argless `rc-server` verbs — `Bash(.hermit/bin/hermitd-run rc-server start)`, `Bash(.hermit/bin/hermitd-run rc-server stop)`, `Bash(.hermit/bin/hermitd-run rc-server status)` and `Bash(.hermit/bin/hermitd-run rc-server gc)`. The first four, the two `backup` verbs, and the four `later` verbs are prefix rules over their arguments; the `rc-server` four are exact-match, since no argument follows the verb — which also means a decorated call (a pipe, a redirect, a `timeout` wrapper) falls outside them and re-prompts. `later add`, `later check` and `task-check.ts` stay with the prompt or the classifier; both check runners execute stored shell commands. No literal task grant exposes a check-result mutation. They pre-clear only those calls — the send, observation and task routes reached during a turn, the `later` four from later bookkeeping, the `rc-server` four reached through the operator-invoked `rc-gate` skill; every other maintenance script still cannot rely on base permissions to pre-clear its calls before the classifier. Documented fallback: 3 denials in a row or 20 total drop auto mode back to prompting ([permission modes](https://code.claude.com/docs/en/permission-modes), [auto-mode config](https://code.claude.com/docs/en/auto-mode-config)), which on a managed session is an unanswered prompt. What auto mode drops is **execution** rules only: a blanket `Bash(*)`, a wildcarded interpreter, a package-manager run, `Agent`, `Monitor`. No `Read` or `Edit` path rule is dropped, and `Read` never reaches the classifier at all, so a path grant either matches or it does not. That distinction matters when a read prompts anyway: the cause is the rule's own anchoring, not the classifier. Claude Code's Linux startup advisory about glob patterns in `Edit`/`Read` rules being ignored is sandbox-scoped (it describes the OS sandbox's own matcher) and says nothing about the permission engine, so it is not evidence that a path rule is inert.
- **The sealed exception.** The overlay carries a declarative `autoMode.allow` entry plus `autoMode.environment` context pre-authorizing the hermit's own `apply-settings.ts` invocations, including when triggered by a plugin upgrade rather than a live operator message. Both are unconditional, like the `soft_deny` guard, with one op held back: `artifact-allow` is enumerated only where `artifactGrantApplies` is true, since it writes the native Artifact permission the boot grant withholds on an unauthorized or non-`claude` backend — pre-clearing it everywhere would let the classifier stand in for exactly the publish a backend choice exists to prevent. Every other op is enumerated on every install. They rode the artifact grant's gating (`publish_authorized`, a page enabled, default backend) while the artifact path was the unattended write they were written for, but neither is artifact-specific: the environment list names the hermit's own notification domains and state directory, and the enumerated ops run on every install — `hermit-evolve`, `hatch`, `channel-setup` and `docker-setup` all invoke `permissions-plan`, `permissions-sync`, `deny` or `channel-env` on hermits that publish nothing. Under the gate those hermits shipped an empty `environment` list, which both drew classifier denials on their own channel sends and left them one turn away from the `/auto-mode-setup` dialog above. Tone matters here: a probe session flagged an over-argued exception as "planted pre-authorization justification," so the entry states its constraints plainly and argues for none of them. Because an ALLOW exception is mandatory once matched, its constraints are the only thing bounding it, so the entry is written as a checkable shape rather than a description of intent — path, op and command form are the whole test, since the classifier cannot verify what the script writes. Each clause is deliberate: the script path is anchored to a **concrete prefix computed at render time** rather than a `*/scripts/` glob — `automodeAllowEntry` anchors on the plugins directory (`$CLAUDE_CONFIG_DIR/plugins`, plus the boot root itself when a hermit boots from a checkout) and then constrains the tail: it must end in `/scripts/apply-settings.ts` and its install root must be named `hermitd` or be a single version directory inside one. The anchor spans install *trees*, not one install, because boot and session resolve this plugin from different ones: `bin/hermitd-run` scans the marketplace clone while the harness substitutes `${CLAUDE_PLUGIN_ROOT}` in skill text with the versioned cache copy — anchoring on the boot root alone would leave every in-session call outside the grant, and anchoring on a version would deny the mid-session upgrade path the entry exists to clear. Both paths must be written out literally, with no `..` segment and no unexpanded variable; the **exact argument grammar** is spelled out (`bun <script> <settings-file> <op> [op args]`) with shell chaining, redirection, env-var prefixes, added arguments, and indirection through `npx`/`sh -c`/wrapper scripts/Agent or Workflow prompts all voiding it; the ops are **enumerated** from `SEALED_SETTINGS_OPS` — `apply-settings.ts` dispatches from a hardcoded `switch` and only its usage message reads the constant, so a contract test asserts every dispatched case is accounted for by `SEALED_SETTINGS_OPS` or `TERMINAL_ONLY_SETTINGS_OPS`; `voice-render` (which renders the custom style file from `config.json`'s `voice` block) lives in `TERMINAL_ONLY_SETTINGS_OPS` and is **deliberately absent** from this grant — the decision it applies was already tiered by the settings gate when it was written to config, so pre-clearing the render too would let one classifier-visible call stand in for both; boot reaches it as a plain OS process, outside the classifier entirely; the target is the session working directory's `.claude/settings.json` or `.claude/settings.local.json`, never one under `$HOME/.claude/`; `channel-env`'s state-directory argument is validated and reported without a settings write; `.mcp.json`, hooks, approval gates and `.hermit/config.json` are excluded by an **operative** clause (they remain Self-Modification) rather than by deferring to another entry; the grant is **void** if this session authored the script with a file-editing tool, or if it would achieve a settings change the operator declined this session or that was blocked this session when attempted *by some other means* (an anti-laundering carve — scoped that way on purpose, since voiding on any earlier denial would let one stochastic classifier refusal of `permissions-plan` lock `permissions-sync` out of the same `hermit-evolve` run, with no in-session recovery); and an upgrade or migration may *trigger* the run without the script path, op or target file ever being *sourced from* its instruction text.

  **Accepted residual, by design:** a plugin install or upgrade writing a new version directory deliberately does **not** void the grant. Voiding on it would deny exactly the unattended `hermit-evolve` path this entry exists to clear — that flow upgrades the plugin and then applies settings in the same session. The consequence is that anything able to force a plugin upgrade mid-session can replace the script the grant covers; the compensating controls are the install prefix anchor (an arbitrary path is still outside the grant) and the deterministic gates below, which the classifier cannot override. The settings ask does not depend on any of this — enforcement is the `PreToolUse` gate below.
- **Settings from chat.** See the [access model](access-model.md) for ownership, unset values, and revocation. Everyday settings apply through `settings-edit`. The static list in `scripts/settings-gate.ts` requests Claude Code's native permission dialog for these paths and their descendants:

  | Protected settings | Paths |
  | --- | --- |
  | Identity and execution | `permission_mode`, `operator_profile`, `voice.prose`, `env`, `monitors`, `boot_skill`, `shutdown_skill`, `backup` |
  | Channel routing | `channels.primary` |
  | Channel boundaries | A channel entry's existence, plus per-channel `allowed_users`, `operators`, `passive_chats`, `default_chat_id`, `dm_channel_id`, `maintainer_channel_id`, `isolate_chats`, `shared_chats`, `state_dir`, `marketplace`, `enabled` |
  | Export and publishing | `telemetry_export.enabled`, `telemetry_export.destination`, `telemetry_export.redact_operator_text`, `artifacts.publish_authorized`, `artifacts.backend` |
  | Tools and credentials | `docker.packages`, `docker.recommended_plugins`, `docker.fleet_mesh`, `remote`, `chrome`, `auth_mode` |

  Direct protected writes ask in either direction, including unset and redundant writes. A parent replacement asks only when protected content is added, changed, or removed. Replacing `voice` while keeping its prose unchanged, or replacing a channel while changing only `morning_brief`, is everyday. Creating a channel entry is the exception that needs no protected key of its own: absent `enabled` means enabled and absent `allowed_users` means accept-all, so a parent write that adds `channels.<name>` asks even for a bare `{}`; dropping one is de-escalation and names only the protected keys it removes. Comparison uses raw stored values: absent and null differ, object key order does not matter, and array order does. An opaque parent write or unreadable comparison baseline asks rather than assuming protected content is unchanged. A parent write after another shell command also asks because that command may change its working directory or baseline. So does an unquoted `{…,…}` value, which the shell brace-expands into argv the command text does not show.

  Routine prechecks retain their separate rule: direct `routines.<index>.precheck` and `precheck_timeout_s` mutations ask, including unset. A routine-container replacement asks when it adds or changes a precheck; removal and reordering with unchanged prechecks stay silent. This checkpoint registers unattended execution; it does not freeze the referenced script's contents. Routine/session-check commands, schedules, model tuning, budgets, escalation, lifecycle, and recording preferences gain no new gate.

  A target spelled through a shell variable and direct Edit/Write, redirect, `cp`/`mv`/`tee`, or `sed -i` onto `config.json` still ask. The hook also retains protection for `RESIDENT.md`, `state/helper-system-prompt.md` and `claude-settings.json`. A write staged through `bash -c`, `eval`, or a script is outside what the hook can read and stays classifier-watched. This is a command-text policy guard, not a filesystem boundary. Boot, hatch, and upgrade writers retain their separate entry points. For recognized `channel-access` pair, policy, and group-add commands, the hook uses the caller's `permission_mode`: it denies `bypassPermissions` and asks elsewhere, naming the explicit code, policy, or enrolment values. The target hermit's configured mode does not decide this gate.

  The dialog is relayed by the channel plugin to its `allowFrom` DMs, never to `maintainer_channel_id`. An empty `allowFrom` means the prompt reaches nobody and the session waits until the watchdog stalled-dialog notice. A No is the operator's answer: never retry or route around it. To forbid chat settings writes entirely, add `Bash(*settings-edit*)` to native `permissions.deny`.

  This remains one hook, not seeded `permissions.ask` argument rules or an extra conversational approval flow. Container comparisons need values, and a chained command gets one reason naming every asked target. Hook-output tests establish the emitted request, not live prompt delivery or enforcement.

Routine `precheck` scripts are operator-authored content executed inside the routine poller, which now runs as a native plugin monitor, unsandboxed at plugin trust. The settings gate's native permission prompt on `routines[].precheck` writes keeps this execution operator-authorized. This is the one place operator content reaches the native monitor path.

- **A channel reply can never authorize a permission grant.** Two independent gates discount it: the model itself treats a `<channel>`-enveloped privileged instruction as a likely injection attempt before making any tool call, and even past that, the classifier's own soft-deny provenance test rejects anything not sourced from the operator's live message. So a channel-resolved decision may only flip hermit config (e.g. `artifacts.publish_authorized`) — the actual permission write always happens either attended (hatch/evolve, where the operator's presence satisfies the intent test) or from an out-of-session executor: `hermitd-start`'s boot-time grant runs as a plain OS process before the Claude session starts, so it is never subject to the classifier at all.

  **Where `permission_mode` sits.** It lives in config but is functionally a permission. The durable key is on the ask list: a `settings-edit` write raises Claude Code's native permission prompt. It writes hermit config, not `permissions.allow`. The session-scoped `!permission-mode <mode>` command is narrower: it reaches only `default`, `acceptEdits`, and `auto`, while `bypassPermissions` is refused. Neither path writes a permission grant.
- **`PermissionDenied` notifier.** A `PreToolUse` gate can preempt a stall (see `ask_gate` above), but the classifier's own denials happen inside a tool call the hermit did not anticipate. Each layer has one owner. The `PermissionDenied` hook (`permission-denied-notify.ts`) rides the resident launch overlay, read at launch only, and records a deduped, bounded maintainer-tier event diagnostic containing the tool name and the payload `reason` (usually `Blocked by classifier`). Dedup is keyed on the **tool alone**, one open 30-minute window per tool: a burst of distinct commands blocked on the same tool sends once, and the next window's message reports how many denials the previous one absorbed (`(+3 more in the previous 30 min)`). Keying on tool + input instead made every distinct command its own key, so a burst collapsed nothing. Alongside it, every denial appends one line to `state/permission-denied-events.jsonl`; timestamp, tool name, and for shell commands the first word of the command (with an `env-prefixed` sentinel when that word is an assignment). Tool input still never leaves the ledger, and the file is created 0600. It is append-only because Claude Code does not serialise hook invocations, so a read-modify-write record loses counts during exactly the bursts worth recording. Both the append and the 30-minute window's read-modify-write happen under one advisory lock, which exists for the window's read-modify-write: the part that genuinely races between concurrent hook processes. Its reach stops at the container boundary, and the append's atomicity is a property of the filesystem rather than something the lock supplies (§ JSONL Ledger Durability). Lines that cannot be read back as a denial are counted in the doctor row rather than silently skipped, so a torn write shows up as a warning instead of an undercount. `hermit-doctor`'s `classifier-denials` check digests that log over a rolling 7 days, and carries the same maintainer-tier restriction, declared as `tier: maintainer` in the check's own output: doctor's notice splits by audience and the row rides its maintainer leg alone, which `channel-send.ts` routes to the maintainer chat, else the primary chat on a `technical` profile, else `state/watchdog-events.jsonl` on a `non-technical` one. Routing follows the general tiered-disclosure policy below rather than being an exception to it. Channel reachability gates only the POST: an absent, ineligible, or unhealthy channel still records the diagnostic to `state/watchdog-events.jsonl`, for later diagnosis. There is no client leg, and the hook never retries the denied call. The model tries permitted alternatives first and uses ordinary blocker handling only if operator action is still required. `transcript-digest.ts` owns the aggregate `tool_rejections.automode-blocked` count, which the reflect flow evaluates separately.
- **Tiered disclosure.** On a client-facing install (`operator_profile: "non-technical"`, or any channel with a `maintainer_channel_id`), operator notifications split by audience. The **maintainer chat** receives technical, operational, and spend content: tool names and denial reasons, USD/cap figures on a budget alert, watchdog lifecycle events, and the reauth sign-in link. The **client chat** receives only plain-language alerts with no tool detail, figures, or internal IDs, and it always receives the ask itself: a notice requesting a decision, reply, or action carries a plain client leg, with the maintainer chat getting the technical companion, never a replacement. The `PermissionDenied` diagnostic is maintainer-tier with no client leg, but it is not an exception to this routing: like every other technical leg, `non-technical` suppresses it to Findings rather than the client chat (fail-closed on disclosure), while a `technical` install with no `maintainer_channel_id` delivers it to the primary chat, which on that profile is the maintainer's own. Maintainer-tier sends carrying credential material (the reauth link) are marked sensitive and skip the searchable channel log. A maintainer chat is **outbound-only for control**: control commands (`!pause`/`!resume`) and reauth code replies still come through the primary DM chat, where `isTrustedController` anchors. It never controls who may reach the hermit, and it cannot pause, resume, or interrogate the session. Adding a `maintainer_channel_id` therefore widens what the hermit tells a second chat. Ask-listed settings writes from any chat raise the native permission prompt instead; everyday settings apply from any chat that reaches the hermit. The model composes both audience versions and delivers them through `channel-send.ts --notice` (a direct platform POST with the bot token and config-pinned target); deterministic callers use the equivalent `--tier maintainer` mode. Neither path touches the channel plugin's `access.json`; the maintainer chat needs the bot present, not an access grant.

## JSONL Ledger Durability

- **Ten ledgers, one of them locked.** `state/permission-denied-events.jsonl` (written by `scripts/permission-denied-notify.ts` from the resident launch overlay, read at launch only) is the only one written under an advisory lock. `observations.jsonl`, `proposal-metrics.jsonl`, `routine-metrics.jsonl` and `settings-audit.jsonl` go through `scripts/lib/append-jsonl.ts`; `cost-log.jsonl` through `scripts/lib/cost-log.ts`; `usage-metrics.jsonl` through `scripts/lib/usage-ledger.ts`; `watchdog-events.jsonl` through `scripts/hermitd-watchdog.ts`; `channel-replies.jsonl` through `scripts/channel-hook.ts`; `update-history.jsonl` through `scripts/hermitd-update.sh` and `scripts/hermitd-docker.sh`. None of those nine take a lock, so the constraint below belongs to the ledgers generally and not to the one file that happens to be protected.
- **What the append relies on.** Every writer is `fs.appendFileSync`, i.e. `O_APPEND`. Rows are far under `PIPE_BUF`, so concurrent appends do not interleave on Linux, and concurrent hook processes inside one container share a kernel and a mount and serialise there whatever the backing filesystem. Why these ledgers are append-only rather than read-modify-write is `docs/architecture.md` § state/ ownership model; the per-line size bound is `docs/artifact-naming.md` § state/.
- **One ledger already has a host-side writer.** `update-history.jsonl` is appended by `scripts/hermitd-update.sh` and `scripts/hermitd-docker.sh`. These plugin scripts run on the host through the project wrappers or `hermitd update`, so the same project ledger is reachable from the host and from inside the container. It is the one ledger that already satisfies the "writer outside the guest kernel" precondition below without a second writer having to appear; the other nine are container-side only today.
- **Where that stops.** A FUSE-backed bind mount is not guaranteed to preserve it. `state-templates/docker/docker-compose.hermit.yml.template` bind-mounts the project tree `${PWD}:${PWD}`, so under Docker Desktop for macOS these ledgers sit on VirtioFS. The mechanism is real and was patched once upstream in QEMU's virtiofsd ([2019](https://lists.nongnu.org/archive/html/qemu-devel/2019-10/msg06043.html), by stripping `O_APPEND` in writeback mode so the kernel owns the semantics), but it needs writeback cache, which is opt-in where [write-through is the FUSE default](https://www.infradead.org/~mchehab/kernel_docs/filesystems/fuse-io.html), and it needs a writer outside the guest kernel. Unverified here: it requires a Mac, which neither this project nor its CI has. Tracked in [#860](https://github.com/gtapps/hermitd/issues/860).
- **The lock does not close that gap, and cannot.** `scripts/lib/lockfile.ts` records the holder as a bare PID and tests liveness with `process.kill(pid, 0)`. The compose template declares no `pid:` key, so the container runs a private PID namespace and a host-side process ends up evaluating a container PID against the host PID table. `pidAlive()` maps EPERM to not-alive (deliberately, so an unrelated pid-reused process cannot wedge the lock), so the likely outcome is a host process judging a live container-held lock stale and stealing it. The lock serialises writers within one PID namespace, and only there. A host-side script taking the same lock would not help; it would need a namespace-independent holder identity.
- **The wider unlocked write.** `pruneJsonlIfHeadStale()` in `append-jsonl.ts` is a whole-file read-modify-write (temp file plus rename) under no lock at all, so a concurrent append landing between the read and the rename is lost. It is bounded by the head gate to roughly once per retention period per install, but it is a strictly larger hazard than the interleaved append, and it applies to every ledger rather than to macOS alone.
- **Accepted, with detection instead of prevention.** The cross-boundary failure needs macOS, Docker Desktop, writeback cache enabled, and a host-side writer racing a container-side one on the same ledger. No corrupt ledger has been reproduced. Two interleaved JSON objects almost always fail `JSON.parse`, doctor validates these files per line (tolerating a genuinely unterminated final line as a partial write), and `hermit-doctor`'s `classifier-denials` check counts the rows it cannot read back rather than skipping them, so a torn write surfaces as a warning carrying that count rather than a silent undercount.

## Script Argument Trust

The sealed allow-list grants whole scripts, not individual invocations: `Bash(bun */scripts/proposal.ts*)` pre-approves **every argument** that call can carry. Outside auto mode those wildcards resolve normally — probed live on CC 2.1.220, a command matching a mid-string `*` rule runs with no prompt — so a script reached this way must treat its own argv as untrusted input. The `Bash(bun */scripts/channel-access.ts*)` entry also pins its state directory; its `group-add` write raises the settings-gate ask despite the allow entry. Two argument classes were reachable before this was enforced:

- **The state dir.** Every production call passes the literal `.hermit` from the project root, but the argument was taken as given, so a single pre-approved call could resolve, dismiss, or patch *another project's* proposals. `proposal.ts` now pins it: the argument must resolve to `hermitDir()` for the current project, and a mismatch is a usage error (stderr, exit 1) rather than a stdout verdict, because several verbs own distinct stdout grammars their callers branch on. The shared check is `assertStateDir()` in `scripts/lib/cc-compat.ts`. It accepts two roots, not one: `hermitDir()`, and the main checkout's state dir resolved via `git rev-parse --git-common-dir`. The second is required because hermit state is deliberately main-rooted and shared across worktrees, so a worktree session legitimately passes main's absolute path; and for an out-of-tree worktree (`git worktree add ../wt`) the walk-up cannot reach main and fails open to the projection. Pinning to `hermitDir()` alone breaks every proposal write from a worktree; the exact case `proposal.ts` exists to serve, since Write/Edit are blocked there. The git lookup runs only after a mismatch (so the common path spawns nothing) and resolves from our own cwd, so it can never name a foreign project. On the argv side, `assertStateDir()` first normalizes a worktree *projection* (the `.worktreeinclude` copy: config.json present, no `state/`) to the root its own walk-up finds, so the relative `.hermit` the CLAUDE-APPEND commands pass resolves to main from inside a worktree instead of being refused. That is not a widening; the normalized root still has to equal one of the two accepted roots, so a foreign projection normalizes to its own foreign root and is rejected exactly as before. `manifest-seed.ts`, `reflect-precheck.ts`, `channel-log.ts`, `observations.ts`, `evolve-finalize.ts`, `transcript-digest.ts`, `channel-send.ts` and `conversation.ts` all adopt the same `assertStateDir()` pin; the conversation script needs it because `thread-create` reads the bot token and `history` opens the channel log. One carries a narrower shape: `transcript-digest.ts` pins only an *absolute* argv, because a relative one is deliberately ignored in favor of the `hermitDir()` walk-up and pinning it would turn that cwd-drift fallback into a refusal. A third, `channel-send.ts`, pins the full argv but exits **2** on a mismatch rather than the shared helper's 1, because it documents 1 as "a leg failed to land" and 2 as "the caller got it wrong, nothing was sent"; a foreign state dir is the latter, and reporting it as the former would read as a broken channel. `channel-send.ts` is the sharpest instance of this class: it is an egress path, so an unvalidated root meant sending with *another* project's bot token to *that* project's configured chat. `evolve-plan.ts` is the one directly-granted script left unpinned, and deliberately: it writes nothing. `reflect-precheck.ts` forwards its argv to `archive-raw.ts` and `update-reflection-state.ts` as a subprocess argument, so its pin covers those hops; but **a forwarding pin is not a substitute for a script's own.** `archive-raw.ts` is covered by that forwarding pin. **When auditing this class, enumerate the sealed allow-list in `apply-settings.ts`, not the call graph**; a direct grant means a direct entry point.
- **A file (or subdirectory) inside the state dir, not the state dir itself.** `update-reflection-state.ts`'s argument is the reflection-state *file*, and `generate-summary.ts`'s CLI-mode argument is the `<hermit>/state` subdirectory — an exact-equality check against `hermitDir()` would reject every legitimate call. `assertUnderStateDir()`, alongside `assertStateDir()` in `cc-compat.ts`, checks containment (resolves under one of the same two accepted roots) instead of equality. `update-reflection-state.ts` was the worst-shaped instance of this defect class before the fix: its argument was a **file path**, not bounded to a directory at all, so an unvalidated call could write arbitrary JSON at arbitrary depth on disk. `generate-summary.ts`'s **hook mode stays unpinned deliberately** — it derives its path from a PostToolUse payload for a write that already happened, and a hook is not reachable through the `Bash(...)` grant the CLI path is.
- **Path fragments joined onto a state-dir subpath.** `proposal.ts patch` joined its filename onto the proposals dir unvalidated, so a `../` prefix reached any frontmatter-bearing `.md` on disk at arbitrary depth. It now requires a direct-child basename. Absolute paths were never an escape here — `path.join` re-roots them — and a regression test pins that.
- **Test-seam flags that accept caller-supplied state.** `domain-hatch.ts` carried `--state-dir`, `--project-root` and `--plugin-list-file` purely so its tests could avoid shelling out to a live `claude`. All three were reachable in production through the `Bash(.hermit/bin/hermitd-run domain-hatch <verb> *)` grants. The first two are the same state-dir defect as above; `--plugin-list-file` is worse — a forged plugin list steers `resolvePlugin()` → `installPath` → `planBlock()`, which reads a CLAUDE-APPEND block from that path and writes it into the operator's `CLAUDE.md`, so a forged list is attacker-authored content landing in the file that steers the agent. Rather than validate these, all three were **removed**: `stateDir`/`projectRoot` are now always derived from `hermitDir()`, and the plugin list is always live. Argv beyond `<plugin-id>` is now allow-listed per verb, exiting 1 with `unexpected_args` on anything else. Tests exercise the removed seams' old coverage at the library boundary (`lib/domain-hatch/preflight.ts`, `target.ts`) with explicit roots, rather than through CLI overrides.

`proposal.ts quality-gate` (reached as a verb, not a standalone script) was checked during this pass and needs no change: it falls through to `proposal.ts`'s own `requirePinnedStateDir()` before ever reaching `lib/proposals/quality-gate.ts`.

**The sanctioned override is an env prefix, and that is what makes it a boundary.** `hermitDir()` honors an absolute `AGENT_DIR` ahead of the cwd walk-up, which is how tests target a scratch state dir. Probed on CC 2.1.220: `AGENT_DIR=/tmp/x bun <dir>/scripts/literal.ts go` requires approval even though the identical command without the prefix is covered by an allow rule — an env assignment moves the command outside the rule's prefix match. So redirecting a hermit script at a foreign root cannot be done silently under the sealed grant.

Applies to any script reached through a wildcarded interpreter grant, not just `proposal.ts`. When adding one, assume its arguments are attacker-chosen and validate the state dir (or, if the argument is a file/subdir under it, use `assertUnderStateDir()`) and any joined path fragment. Prefer removing a caller-supplied override entirely (as `domain-hatch.ts` now does) over validating it, when nothing production-side actually needs the override.

## Bash Sandbox

Hermit does not probe for or configure Claude Code's native bash sandbox (`sandbox.*` settings, `bwrap`/`sandbox-exec`). Predicting whether CC's own sandbox spawn would succeed from outside CC proved unreliable — a false-positive probe could enable a sandbox profile that then broke every subsequent Bash call, with no in-session recovery. `/hatch` instead prints a one-time pointer to CC's own setup: run `/sandbox` (its Dependencies tab checks `bwrap`/`socat` for you) or see the [sandbox docs](https://code.claude.com/docs/en/sandboxing).

**Docker:** `bubblewrap`/`socat` stay installed in the hermit image so `/sandbox` is available in-container if you want it, but hermit writes nothing (Claude Code's sandbox is off by default). The container boundary (`cap_drop:ALL`, `no-new-privileges`, network policy) is one of the isolation approaches Anthropic lists for unattended runs, alongside VMs and the sandbox runtime — required under `bypassPermissions`, defense in depth under the default `auto` mode — and the nested bwrap sandbox is further optional depth on top of it (https://code.claude.com/docs/en/sandbox-environments). Note: on Ubuntu 24.04+ hosts (`kernel.apparmor_restrict_unprivileged_userns=1`, the 23.10+ default) the AppArmor `docker-default` policy blocks `bwrap` from creating user-namespaces in-container, so an in-container sandbox may not start there and — if forced on regardless — would silently kill heartbeat and `/watch` Monitor subprocesses.

**Enabling or disabling:** entirely the operator's call — run `/sandbox` or edit `sandbox.enabled` in your settings file directly. Hermit never writes this key.

**Credential protection:** Claude Code's default sandbox read policy still allows reads of `~/.aws`, `~/.ssh`, and `~/.gnupg`. If you enable the sandbox, add a `sandbox.credentials` block (or `sandbox.filesystem.denyRead`) to block them — earlier hermit versions wrote these denies for you, but hermit no longer manages `sandbox.*`, so this is now yours to set. See the [sandbox docs](https://code.claude.com/docs/en/sandboxing#protect-credentials).

**Custom CA / MITM proxies:** tools that use a corporate proxy with a custom certificate authority may need `"enableWeakerNetworkIsolation": true` in the `sandbox` block. See the [FAQ](faq.md) for details.

## Login Token Handling

Docker hermits on subscription auth can hold a long-lived `setup-token` (offered right after login in `/docker-setup`; a hermit that declines stays on its `/login` credentials and none of the below applies). Renewal relays through the operator's chat channel, so it's worth being precise about what crosses that channel and what doesn't.

**Crosses the channel:** the one-time OAuth sign-in URL, and the short-lived login code the operator pastes back. Both are single-use and worthless once the flow completes. On an install with a `maintainer_channel_id` configured, the URL is routed to the maintainer chat (via `channel-send.ts --tier maintainer`, marked sensitive so it is not written to the searchable channel log) rather than the primary client chat; the operator still pastes the code back through the primary DM chat, which remains the only inbound surface.

**Never crosses the channel:** the token. It is captured from the mint process's own terminal pane and written directly to a `0600` file on the container's config volume. It is never printed to stdout, never logged, never included in a channel message, and never returned by any script that a skill or the model can read — the install path returns only `{ok, expires_at}`. The renewal skill relays a link it was handed; it never sees the credential.

**Where the token lives, and where it doesn't:**

| Location | Holds the token? | Why |
| --- | --- | --- |
| `<config-dir>/.hermit-setup-token` | Yes, `0600` | Persistent volume, survives restarts, rotatable in place |
| `state/setup-token.json` | No — only `{minted_at, expires_at}` | Doctor and the watchdog need expiry, not the secret |
| `.env` / docker-compose | **No, deliberately** | `env_file` applies at container creation, so a token there could not be rotated without a host-side recreate |
| `<config-dir>/.hermit-login-staging/` | Yes, transiently, `0700` | Where a relayed claude.ai sign-in lands in `auth_mode: login`. Emptied before each attempt, removed on abort, and consumed by the watchdog's commit during the next restart — so it holds a live credential only between a sign-in and the restart that follows it |
| `state/pending-credential.json` | No — only `{staged_dir, staged_at}` | The watchdog needs to know a credential is waiting, not what it is |
| `state/relay-unreachable.json` | No — only `{at}` | A suppression timestamp; carries nothing about the operator or the credential |
| tmux env-file (`/tmp/.hermit-env-*`) | Transiently, `0600` | Sourced then deleted by the shell that launches claude |
| Mint pane scrollback + capture file | Transiently, `0600` | Both destroyed on every exit path, including aborts |

The reactive recovery path runs entirely in the watchdog with no model involvement — a hermit with a lapsed login cannot reason, so the flow that recovers it must not depend on reasoning. It also waits for an explicit operator acknowledgement before minting anything, so an attacker who can observe the channel still cannot cause a link to be issued on demand.

## Container Hardening

`/hermitd:docker-setup` (v1.0.26+) renders three kernel-enforced hardening stanzas into `docker-compose.hermit.yml`. These are defense in depth — they reduce the blast radius of a successful prompt injection or a compromised plugin. They are **not** a substitute for the upstream defenses (deny patterns, non-root user, named-volume isolation, no host secret mounts) and they don't make the container "safe against prompt injection." They make a successful injection less useful.

Honest weighting:

| Stanza                                   | What it does                                                                   | Real teeth?                                                                                                 |
| ---------------------------------------- | ------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------- |
| `security_opt: [no-new-privileges:true]` | Blocks setuid escalation at the kernel level, even via planted setuid binaries | **Yes** — closes a real vector against future supply-chain compromise of any installed plugin              |
| `cap_drop: ALL`                          | Revokes Linux capabilities (NET_RAW, SETUID, DAC_OVERRIDE, …)                  | Incremental — non-root `claude` user already had no ambient caps; this closes the kernel-enforced ceiling  |
| `pids_limit: 2048`                       | Caps process count (fork-bomb / runaway-subprocess bound)                      | Resource bound, not a security primitive on its own — limits collateral damage                             |

Hermit's runtime (tmux, claude CLI, bun, jq, npm, git+HTTPS plugin installs) needs none of what these stanzas remove. Steady-state PID usage is ~80; install bursts can spike higher but stay well below 2048.

**Override path.** Operators with custom workloads (services on ports <1024, setuid helpers, high-PID frameworks) edit `docker-compose.hermit.yml` directly to relax or remove the relevant stanza. The defaults are conservative because the recommended-plugins flow accepts third-party marketplaces — every operator who didn't audit every plugin benefits from the floor.

**Verifying it's active.** From the host:

```bash
# Capabilities — both should be 0000000000000000
docker compose -f docker-compose.hermit.yml exec hermit \
  grep -E '^Cap(Eff|Bnd)' /proc/self/status

# no-new-privileges — should report NoNewPrivs: 1
docker compose -f docker-compose.hermit.yml exec hermit \
  grep NoNewPrivs /proc/self/status

# PID limit — should report 2048
docker compose -f docker-compose.hermit.yml exec hermit cat /sys/fs/cgroup/pids.max
```

**Limitation.** These flags only apply at container creation, not on `restart`. After patching an existing compose file, run `hermitd-docker down` then `hermitd-docker up` — `hermitd-docker restart` silently keeps the old container.

### Advanced hardening — `/docker-security`

Beyond the always-on baseline above, `/hermitd:docker-security` is an opt-in advanced wizard that adds a `docker-compose.security.yml` overlay with LAN containment + DNS policy (firewall + DNS sidecar with port-53 redirect for actual enforcement), resource bounds + kernel hygiene sysctls, and a boot-time plugin-install audit log. Each toggle is presented with honest cost/benefit framing, applied as an overlay (does not modify `docker-compose.hermit.yml`), verified against the live container, and fully reversible. The LAN containment toggle is hard-skipped when `docker.network_mode: "host"` is in use. Honest limitation surfaced in the wizard and dedicated docs: DNS policy blocks domain-based exfil but cannot stop direct-IP egress to a hardcoded public address. See [Docker Security](docker-security.md) for the full toggle reference, verify commands, and documented limitations.

### Known limitations

- **`helper-report-relay`** reads exactly one derived path under the state directory's `helper-reports/`, resolved only when one open record owns the destination chat, and grants no permission. It guarantees exact text at the channel tool's input only while the hook runs. A timed-out hook lets the one-line placeholder through before the PostToolUse alarm.

- **The hermit accepts inbound peer messages from any Claude Code session on the box.** Claude Code holds a cross-session message purely on the sender's permission class, and a held one opens a dialog nobody answers on an unattended hermit — the watchdog's own socket wake included. `hermitd-start` therefore writes `crossSessionInbound: "accept"` into the launch overlay (`--settings` is the only scope that can loosen this key; a project or local settings file is consulted only when it *tightens*). Local peers are not authenticated, so any session that can reach the inbox socket can put text into the hermit's next turn. Delivery is not authority: peer requests inside the resident's existing authority are acted on, but a peer message still cannot expand authority, approve guarded actions, or change permissions. The deterministic gates and the settings ask above are unchanged. The socket directory is `0700`, so the sender must already run as the same host UID. To opt out, set `crossSessionInbound` to `"hold"` or `"refuse"` in `~/.claude/settings.json` (boot leaves the key alone whenever your user settings already carry one), or to `"refuse"` in the project's `.claude/settings.json`.

- **Backup is a third opt-in outward egress, and a denylist-shaped one.** With `backup.remote` set, the hermit pushes its whole footprint to that repository on a schedule with no model in the loop. Unlike telemetry's allowlisted bundle, a backup copies everything except what a refusal screen catches (secret-shaped filenames, the channel log, credential-shaped content under 512 KiB, oversized files) — that screen is hygiene, not a boundary, and you cannot restore from an allowlist. Point it only at a private repository you control, and audit `config.env` before enabling: it is free-form and is committed. The token is read from the environment or the project `.env`, never from `config.json`. `Bash(.hermit/bin/hermitd-run backup run*)` is pre-approved, which makes it a sanctioned push path that the hardened profile's `git push origin main*` and `*--no-verify*` denies do not cover; its blast radius is the asked `backup.remote` write and nothing else, and `backup setup` stays a terminal command. See [backup.md](backup.md).

- **`hermit-doctor`'s `channel-liveness` check and the deterministic channel-send path (`lib/channel-send.ts`) are two of core's direct outward egress paths.** Doctor's liveness call (Telegram `getMe`, Discord `/users/@me`) sends no message content, 5s timeout, fail-soft. `channel-send.ts` does send message content — it is the mechanism behind the watchdog's lifecycle pushes (restart/wedge/forced-pause), `cost-tracker`'s budget-cap alerts, and the `lib/prompt-stages/channel-status-responder.ts` reply — reading the bot token straight from the already-configured channel's `state_dir/.env` (the same token the channel MCP plugin uses), a plain-text POST with an explicit 10s timeout, and no retry on failure (fail-open: the caller falls back to its existing model-mediated path). Every other doctor check is a local filesystem read, except `peer-inbox`, which opens a local Unix-domain connection to the resident session's own inbox socket and hangs up without writing a frame — no network, no message content. The docker-security DNS allowlist already covers both platform hosts (`telegram.org`, `discord.com`) — no allowlist change needed. Disabling a channel disables both its liveness probe and any push through it; there is no separate per-check opt-out in v1. At container startup, the Docker entrypoint sets the project's `hasTrustDialogAccepted` flag when its own `.mcp.json` declares one or more servers, because a versioned `.mcp.json` is only honoured in a trusted workspace. What justifies the flip is the operator's own workspace-trust decision, which `/docker-setup` walks them through before the container ever starts — not container hardening: an approved server runs with the container user's access to the project bind mount and whatever egress the DNS allowlist permits, exactly as § Plugin Security → Trust Model describes for plugins. Trust the servers in your `.mcp.json` the way you trust the project itself. Trust is not approval: the entrypoint approves no server the project's `.mcp.json` declares, so enrolling one stays an operator act through `enabledMcpjsonServers` in the project's `.claude/settings.json` (see [always-on.md](always-on.md#mcp-servers)). Only the channel plugin ids are approved by boot.
- **Remote control and status disclosure trust the operator DM when no `allowed_users` is set.** A plain channel *reply* still follows the documented accept-all default when `channels.<channel>.allowed_users` is absent — but the two paths that either *mutate state* (`!pause`/`!resume`/`!snooze` via `lib/prompt-stages/pause-keyword.ts`) or *disclose operator state* (the deterministic `!status` reply) do **not**. With no allowlist configured they trust only the operator's pinned home chat (`chat_id === channels.<channel>.default_chat_id`, falling back to `dm_channel_id` until the pin is seeded); any other sender's control keyword is a silent no-op, and any other accepted sender gets a redacted, coarse status (no spend figures, task text, or pending-approval IDs). The anchor is the *pinned* home rather than the last-learned DM because `dm_channel_id` follows whichever chat wrote last: anchoring there meant control authority could be **acquired** by messaging from a new chat. `default_chat_id` is seeded once and moves only from the terminal, so that path is closed. `<channel>` here is the normalized bare server name (`lib/channel-envelope.ts`'s `normalizeChannelSource`) — the harness injects a plugin-qualified `source` on the wire (`plugin:discord:discord`), but config keys channels by the bare name, so this gate resolves the qualified source back to it before every lookup. **Caveat (unchanged by the pin):** if a channel's home *is* a group/server channel, `default_chat_id` equals that shared chat, so every member of it matches the binding — those installs must set `allowed_users` explicitly to restrict control and full status to named operators. Pinning closes the *acquisition* path (a new chat can no longer become the anchor by messaging); it does not narrow a home that is itself shared, because the match is per-chat, not per-sender. The same home-chat binding still governs pause, resume, and status, so on a shared home this caveat still applies. Ask-listed settings writes raise the native permission prompt from any chat; everyday settings writes are not bound to the home chat. Group enrolment from chat is an asked write relayed to every paired DM user, and `channel-access.ts` refuses it under bypass permissions. This is a flat trust list, not RBAC (an RBAC pass on `allowed_users` is a deliberately-deferred enterprise gap).
- **Telemetry export is another direct outward egress — opt-in, off by default.** `config.telemetry_export` (absent or `enabled: false` = nothing ever leaves the box) periodically POSTs a versioned health/cost bundle to an operator-configured webhook from the watchdog tick. The bundle is allowlist-built: only named numerics/enums/counts are copied in by default (cost totals, doctor check statuses, alert counts, session cost/duration, watchdog event counts); free text (task descriptions, error messages, alert detail strings) is included only when the operator explicitly sets `redact_operator_text: false`. The bearer token comes from an env var named in config, never from `config.json` itself, and neither the webhook URL nor the token ever appear in logs or error output. Under docker-security, the webhook's host must be added to the DNS allowlist or exports fail (and spool) inside the hardened container.
- **Three artifact pages publish session-derived content to claude.ai, with per-page toggles.** `config.artifacts.dashboard`/`proposals`/`weekly_review` (default `true`/`true`/`false`) each publish a rendered page — status/latest-brief/proposals/weekly-evolution, open-proposal full text, and the compiled weekly review, respectively — via Claude Code's built-in Artifacts feature, not a hermit-authored HTTP call. **This paragraph describes `config.artifacts.backend: "claude"`, the default; the sentences about the built-in feature, its governing controls, and Anthropic-side privacy do not carry over to any other backend (next bullet).** On the default backend it's the same publish path as any other Artifact a session creates, so it's governed by Claude Code's own controls (`disableArtifact`, `CLAUDE_CODE_DISABLE_ARTIFACT`, `permissions.deny`), not the docker-security DNS allowlist. Private to the publishing account on Pro/Max; Team/Enterprise can additionally Share within the org, never across it. Every automatic publish is a deterministic render of enumerated state files — with one caveat: the dashboard's latest-brief section embeds `state/last-brief.json`, whose `text` field is itself model-composed by the `brief` skill, so that one section is not exclusively machine-generated content. On-demand publish of a compiled doc or proposal (operator-initiated, no config gate) is likewise a direct file publish, no model authorship. A hermit that ran `/hermit-dashboard-design` is the second caveat — see the next bullet. See `docs/config-reference.md#artifacts` and `docs/artifacts.md`.
- **A custom dashboard renderer is operator-owned code core executes on the automatic path.** `/hermit-dashboard-design` writes `.hermit/dashboard-render.ts`, and the file's *presence* — no config flag — makes `artifact.ts render dashboard` `spawnSync` it and publish whatever it produced. Two properties change for that hermit. First, the dashboard is no longer a deterministic render of enumerated state files: its layout, its data selection, and its escaping are model-authored once and then replayed unattended on every brief, so the "no free-form model-authored pages on the automatic path" assurance below holds only for a hermit with no renderer installed. Core validates the receipt, never the page — no structural check, no escaping pass — by design (`docs/artifacts.md` § Custom renderer); the escaping discipline lives in the skill that writes the file. Second, a routine dashboard refresh becomes a code-execution point: whoever can write that path gets code running under the hermit's own identity at every refresh, behind a command line that reads as a core render call. It is a *persistence* surface, not a new privilege — writing it takes the same file-write capability an attacker would already need — but it is durable across restarts and invisible to a reviewer watching Bash commands, so treat an unexplained `dashboard-render.ts` the way you would an unexplained hook. Unlike the sealed-allow-list scripts below, `artifact.ts` takes its state dir as given (it holds no direct `permissions.allow` grant, so every call is classified on its own), which means the executed path follows that argument — audit the argument, not just the verb.
- **A non-`claude` artifact backend sends the same content to a host the operator chose, under the operator's own grant.** Setting `config.artifacts.backend` to a connected MCP artifact server routes every page publish there instead of claude.ai. Registering that server, minting its token and granting its tool permissions are done by the operator by hand: that manual setup, not the config key, is the consent act, and the plugin adds no permission for it. A native `Artifact` publish is denied by the plugin's `PreToolUse` hook (`scripts/artifact-backend-guard.ts`), which names the backend in its reason; the tool and its design skills stay available. `hermitd-start`'s boot grant still covers only the native `Artifact` tool and is skipped on a non-`claude` backend, so an install that forbids publishing to claude.ai does not newly acquire a standing prompt-free grant for exactly that. Skipping is not revocation: a hermit switched over after boots on the default backend keeps the `Artifact` entry already in `permissions.allow`, and removing it is a manual edit. Consequences to weigh: the content is the same session-derived render, but the Anthropic-side privacy and governance properties in the bullet above no longer apply: retention, access control and sharing are whatever that server implements, and its egress is subject to the docker-security DNS allowlist like any other outbound host. Failure is strict-skip, never a silent fallback to claude.ai, so a misconfigured backend cannot leak a page to the other host. Core hardcodes nothing about any particular server; the publish protocol comes from the server's own MCP `instructions`, which also means the trust placed in those instructions is the operator's to assess.
- **`permissions.allow: ["Artifact"]` is a sanctioned pre-approval of an outward-publishing tool for autonomous use.** Applied via the `artifacts.publish_authorized` config flag (§ Auto-mode Classifier above) so unattended sessions don't stall on the first-publish permission ask (a headless "ask" is an effective deny) — a channel reply sets the flag only, and `hermitd-start`'s boot-time grant, running outside any session, is what actually writes the permission (needed because the classifier blocks a session from widening its own `permissions.allow`, even attended-seeded). Re-ensured every boot while authorized and the grant applies, so a hand-wiped entry heals itself. Declining via `/hermit-settings artifact-authorization` sets the flag to `false`: the entry is removed at the next boot, not in-session, from every settings file the plugin wrote it to: `.claude/settings.local.json`, which the boot grant re-ensures, and also the committed `.claude/settings.json` when `state/hatch-options.json` stamps the hatch target `committed`, since that is where `hatch` wrote the original. An install carrying no usable stamp is cleared locally and left alone on the committed side: that entry's provenance is unknown, and removing an operator's own rule is worse than leaving a stale one. A `null` flag leaves an existing entry alone. Assessment: a published artifact is private to the publishing account until someone shares it from the page's share menu, so a prompt-injected publish is persistence/noise rather than exfiltration — reaching an attacker still requires a human to share the page, and `channel-send.ts` (above) remains the materially riskier egress. The real cost is losing the human checkpoint before irreversible external persistence: there is no tool-side delete, and published content may be cached even after removal from the gallery, so a mistaken publish (e.g. a render that embeds a secret that leaked into state) can't be fully recalled. Mitigation: every automatic-path publish is a deterministic render of enumerated state files (no free-form model-authored pages on the automatic path — see the brief-text and custom-renderer caveats above); operators who decline the flag get the same outcome via setup-time banking (first publish happens inline, attended, at hatch/evolve time) instead of a standing grant.
- **Egress filtering is opt-in.** Bridge networking isolates from localhost but the container can still reach the internet by default. A successful prompt injection can exfiltrate data to external hosts. **Mitigation available**: `/hermitd:docker-security` adds LAN containment + DNS policy via a firewall sidecar with kernel-level port-53 redirect for real enforcement. **Remaining gap**: direct public-IP egress (hardcoded IPs, no DNS) is not blocked even with the wizard — v1.1 may add nftset-driven IP allowlisting. See [Docker Security](docker-security.md).
- **No input sanitization for fetched content.** Content fetched from external APIs enters Claude's context unsanitized. Deny patterns cannot catch injection via fetched content; that's an instruction-following boundary, not a mechanical one. **The scheduled-wake surface is now scanned.** HEARTBEAT.md is model-editable and feeds the autonomous evaluation subagent verbatim, so a poisoned checklist item written in one session could steer every future wake. `heartbeat.ts precheck` scans it pre-wake for three pattern classes (instruction-override phrases, context-marker tags, decode-pipes); a hit converts the tick into an operator alert and suspends checklist evaluation until the file is edited. The suspension is scoped to checklist evaluation only; deterministic operator-safety notifications still fire (a pending budget alert pierces the announced-damper), since neither reads HEARTBEAT.md. This breaks the self-persistence path but is defense-in-depth, not a boundary; the PreToolUse/permissions chokepoint remains the actual guard during any wake turn.
- **Seeded permission rules are a blocklist.** They catch the spellings you listed. Equivalent commands not on the list execute normally (or hit the auto-mode classifier). Bind mount scope and network isolation are stronger defenses for novel attacks. The native engine does **not** fold obfuscation: doubled whitespace, unquoted `$IFS`, backslash-newline continuation, and `r\m -rf`-style escapes are not rewritten to the canonical spelling. Redirect twins (`>`, `cp`, `tee`, `sed -i`) were dropped; those side channels are classifier-watched, not a second permission engine. Unicode normalization (NFKC), ANSI/NUL stripping, base64/decode-pipe detection, and general flag-order canonicalization are also absent: Bash does not treat those as equivalent to the canonical spelling (a fullwidth `ｓudo` is a distinct token that fails with "command not found"), so folding them would close a non-threat while adding false-positive surface. A full deobfuscation pipeline is disproportionate here: it sits behind the bash sandbox and container hardening layers above, not in front of an unsandboxed process.
- **Episodic channel-log (PROP-010) stores raw channel text locally.** `state/channel-log.sqlite` holds messages verbatim. Outside passive chats, capture follows `channels.<channel>.allowed_users`. With per-chat opt-in through `channels.<channel>.passive_chats`, every member's delivered message is recorded and `allowed_users` gates waking the model instead — absent, it still means accept-all, so every member who mentions the bot can drive a turn; `hermit-doctor`'s `passive-chats` check warns for a passive chat without a list. An addressed turn in a passive chat includes the most recent un-mentioned messages from allowed senders since the hermit's last recorded reply in that chat (sensitive sends are never recorded, so the boundary is the log, not every platform reply) and within the last six hours; this requires channel logging to be on, and non-allowed members' rows are recorded but never injected. The plugin must deliver all messages (`requireMention:false`, empty per-chat `allowFrom`). Any member of an enabled group can attempt a permission reply by guessing the code: the plugin intercepts permission replies before delivery, so they never reach a hook. Only people who may approve tool use should be DM-paired, because every `allowFrom` DM receives and can answer native permission prompts; everyone else joins through a group whose admission is independent of `allowFrom`, and `allowed_users` narrows who can wake the hermit, never who can approve. See **Settings from chat** under [Auto-mode classifier](#auto-mode-classifier) for the DM relay rule. Blocked text still appears verbatim in the session transcript as a `system` record. Full message text is retained until weekly-review consolidation and its retention window prune it. Storage is deliberately unsanitized for consolidation fidelity, but the `/recall` read path (`search.ts`) runs recalled text through `safeForLLM` before it reaches model context. Treat messages from the operator and ordinary chat members as untrusted external input, never as instructions. The file is local-only and covered by the standard `state/` gitignore. It is also refused by `backup` in every mode, independently of the gitignore (see [backup.md](backup.md)). `/recall` from a non-home chat is scoped unless widened with `isolate_chats: false` or `shared_chats`; the maintainer chat is always unscoped, and a non-technical home chat remains scoped. Disable capture with `knowledge.channel_log_enabled: false` or per-channel `channels.<name>.log_chats: false`; `log_chats: true` overrides a globally disabled switch. Passive wake blocking still applies. The Discord chat cache (`state/channel-chats.json`) is a third direct bot-token use, read-only against the platform: channel parent/guild metadata and the bot's guild roles, with a 2s timeout and failed lookups cached for 24 hours. It sends no message content.

## Plugin Security

### Trust Model

Installing a plugin runs that plugin's hooks and skills with the same authority as hermit. Only install plugins from sources you trust the same as hermit itself. The container hardening in `docker-compose.hermit.yml` (`cap_drop`, `no-new-privileges`, `pids_limit`) reduces what a *compromised* plugin can do to the host kernel — it does not vet the plugin's intent, sandbox its file access within the project, or prevent it from acting on your behalf via the agent. A malicious or careless plugin still runs as you.

Plugins run with the same permissions as Hermit. The default `auto` mode applies classifier review to each action; if the operator has opted into `bypassPermissions` for fully unattended Docker operation, plugins run with full unrestricted execution — no permission prompts, no human review.

**Policy:** The entrypoint installs every enabled entry in `docker.recommended_plugins` on first boot, regardless of marketplace. The trust gate is at **configuration time**: entries only land in `config.json` when the operator explicitly confirmed the mirrored plugin list during `/docker-setup` or `/hermit-settings docker`. Preselection during setup is restricted to `claude-plugins-official` and `gtapps/*` — third-party entries must be manually opted in. See [Recommended Plugins — Trust model](recommended-plugins.md#trust-model).

**No auto-updates:** The entrypoint installs plugins on first boot but never auto-updates them. Plugin updates are operator-initiated via `/hermitd:hermit-evolve` or image rebuild.

**Hermit does not vet, audit, or take responsibility for any plugin.** Even official plugins should be understood before enabling. You are responsible for evaluating what you install.

See [Recommended Plugins](recommended-plugins.md) for the full list and installation instructions.

Resident duties in `.hermit/RESIDENT.md` are appended only by the launcher, and the helper system prompt in `state/helper-system-prompt.md` is written only at boot. Writes to those files and the operator-owned `claude-settings.json` use the same settings gate as config.json, with redirect denies and Edit ask rules.

### Task record script boundary

`task.ts` and `duties.ts` pin their state-directory arguments with `pinStateDirOrExit` before accessing task or duty data, under the Script Argument Trust contract. Their per-script grants are `Bash(bun */scripts/task.ts*)` and `Bash(bun */scripts/duties.ts*)`, installed by sealed `permissions-sync`.

`Edit(*.hermit/tasks/**)` is denied (Edit rules cover every built-in file-editing tool). `Edit(*.hermit/TASKS.md)` asks. The resident uses the validated task verbs as the sole record writer; workers report to it. Policy remains operator-editable; policy text cannot bypass revision, approver, evidence or transition checks.
